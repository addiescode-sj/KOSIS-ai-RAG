# T2-33 v2 골든 질문을 사용자 말투로 (검색 난도 맞추기)

## Goal
- 완료 기준 (TASK.md 그대로): v2 질문은 정답 표의 분류 라벨·항목명을 평균 1.8개 그대로 인용한다(v1 사용자 질문 0.6). 그래서 bm25-record Hit@1이 0.667로 v1(0.250)보다 높다. 질문을 사용자 말투로 다시 써서 라벨 인용 수와 표 이름 겹침을 qtype별로 v1 수준에 맞추고, L1 판정·L3 사실은 유지한다
- Baseline (T2-32 직후, 답 있는 문항, v1은 phase1 출처 제외):

  | 지표 | v1 (사용자 관점) | v2 |
  |---|---|---|
  | 질문에 그대로 인용된 정답 표 라벨·항목 수 (평균) | 0.6 | 1.8 |
  | 〃 concept | 0.1 | 1.4 |
  | 〃 multi_condition | 1.1 | 3.6 |
  | 〃 exact_name | 0.9 | 1.8 |
  | 정답 표 이름과의 글자 bigram 겹침 (중앙값) | 0.21 | 0.25 |
  | 〃 concept | 0.03 | 0.18 |
  | 비슷한 이름의 경쟁 표 수 (평균) | 3.5 | 5.5 |
  | bm25-record Hit@1 / MRR (test) | 0.250 / 0.332 | 0.667 / 0.727 |

  - 경쟁 표 수는 v2가 더 많아 원인이 아니다.
  - 표 이름 겹침은 concept을 빼면 비슷하다.
  - 차이를 만드는 것은 **셀 라벨의 그대로 인용**이다. T2-32 `check_question`이 라벨·항목명을 문장에 그대로 남기도록 강제했기 때문이다.
- 측정 스크립트: 라벨 인용 수 = 정답 표의 `items` + `classes.labels` 중 공백·괄호를 뺀 형태로 질문에 들어 있는 개수('계'·'전체' 제외). 표 이름 겹침 = 질문 글자 bigram 중 표 이름 bigram 비율. 빌더에 함수로 넣고 meta에 qtype별로 남긴다.

- 목표 수치 (리뷰 1 반영): v1의 qtype별 bm25 Hit@1을 v2 qtype 구성으로 가중 평균하면 **bm25-record 0.245, bm25-catalog 0.244**. "사용자 질문 수준"의 기준값으로 쓴다.
  - v1 qtype별 Hit@1 (record): exact_name 0.50 · sibling 0.46 · period_cycle 0.29 · multi_table 0.29 · concept 0.08 · multi_condition 0.00 · ambiguous 0.00.
  - v2 (record): exact_name 0.93 · concept 0.46 · multi_condition 0.50 · period_cycle 0.73 · sibling 0.82.
  - 격차는 exact_name을 뺀 모든 유형에 있다.

## Idea
1. **난도 지표를 빌더에 넣는다**: `quoted_labels(question, table)`, `name_overlap(question, table)`을 qtype별로 meta에 남긴다.
   - 목표는 최소화가 아니라 **v1 분포 구간**이다. qtype별 평균 인용 수는 [v1 − 0.3, v1 + 0.3], 표 이름 겹침 중앙값은 [v1 − 0.05, v1 + 0.05].
   - 너무 낮추면 BM25에만 불리한 집합이 된다(리뷰 4).
2. **셀 고정 규칙 (리뷰 2·5)**: 기존 `item_term`을 라벨에도 넓혀 `terms: {라벨 또는 항목명: 질문 속 표현}`로 쓴다. 표현마다 코드가 확인하는 것:
   - (a) 질문에 그 표현이 들어 있다.
   - (b) 정식 이름과 글자 bigram을 공유한다. 공유하지 않으면 **코드에 둔 일상어 동의어 표**(`USER_WORDS`, 예: 출생↔태어난·아이, 혼인↔결혼, 사망↔돌아가신, 이혼↔헤어진, 가구↔집, 인구↔사람)에 있어야 한다. 동의어 표는 사람이 PR에서 검토하는 고정 목록이다.
   - (c) **유일성**: 그 표현이 같은 차원(또는 같은 표의 항목 목록)의 다른 라벨과도 맞으면 탈락한다. 예: '아이'는 출생건수와 조출생률 둘 다에 맞으므로 탈락. 같은 차원에 다른 후보가 없을 때만 통과한다.
   - 지역명·연도는 그대로 둔다. 다른 숫자 금지에 **한글 수사**(열두 살, 스무 명 …)를 추가한다.
3. **질문 다시 쓰기**: exact_name(20)을 뺀 답 있음 92문항 + L3 전용 거절 20문항.
   - exact_name은 표 이름을 유지한다.
   - 사실·정답 셀·qid는 그대로다.
   - 다 쓴 뒤 문장을 고정하고 나서 측정한다. 측정 결과를 보고 문장을 다시 고치지 않는다.
4. **판정 풀 보충 (리뷰 3)**:
   - `pool`이 이전 `retrieval_pool_v2.csv`의 (qid, key) 판정을 이어받는다.
   - 새로 나온 후보만 규칙 필터 → Claude 판정한다.
   - 이어받기에는 pytest를 남긴다.
5. **L2 갱신**: 기간·연도·지역은 코드로 다시 만든다. measures·dimensions는 바뀐 문장에 맞게 다시 붙인다.
6. **측정**:
   - 난도 지표, L1 bm25-catalog·record(가능하면 chroma·하이브리드도: 공유 서버가 켜져 있을 때만).
   - 같이 잴 것: L2, L4 검색 1위, oracle 재검증(L1 1.0, L3 PASS 100%).
   - 결과 파일은 v2를 갱신한다(T2-32 수치는 plan과 리포트에 남아 있다).

## Option A — exact_name 외 전 유형을 사용자 말투로 (안전장치 포함)
- 접근: 위 Idea 그대로.
- 예상 효과:
  - 라벨 인용 1.8 → v1 구간(0.3~0.9).
  - bm25-record Hit@1 0.667 → **0.245 + exact_name 문항이 v1보다 쉬운 만큼**. exact_name을 v2 값 0.93으로 두면 가중 평균 **~0.31** (*계산*: exact_name만 v2 값, 나머지는 v1 qtype 값).
- 실질 반영 이점: 검색 지표가 사용자 질문 기준이 된다. 검색 개선(T2-06·07·29)을 v2로 보고할 수 있고, L2 파서도 일상어로 평가된다.
- 비용·리스크: 문장 112개 재작성, 동의어 표·유일성 검사·이어받기 구현. 새 후보 판정 행 수는 *미상*(실행 후 기록). 반나절 이상, 오늘 마감과 빠듯하다.

## Option B — v1 사용자 시나리오 질문을 v2에 섞기 (L1·L2 전용)
- 접근: v1에서 phase1 출처가 아닌 107문항을 합친다. 조사 비중이 25%를 넘으면 일부만 넣는다. L3·L4는 v2 그대로.
- 예상 효과: L1 ~220문항. Hit@1은 두 집합의 가중 평균으로 ~0.48 (*계산*: (0.667 × 112 + 0.25 × 79) / 191).
- 실질 반영 이점: 2시간. 사람이 쓴 질문이 그대로 들어간다.
- 비용·리스크: v1 쏠림이 돌아오고, qid가 L4까지 이어지지 않으며, v2 문항 자체는 여전히 쉽다.

## Option C — concept·multi_condition만 다시 쓰기 (리뷰 제안)
- 접근: A의 안전장치를 그대로 쓰되 다시 쓰는 범위를 격차가 가장 큰 두 유형(40문항)으로 줄인다.
- 예상 효과: 그 두 유형만 v1 값이 되면 가중 평균 **~0.51** (*계산*: concept·multi_condition은 v1 값, 나머지는 v2 값 그대로).
- 실질 반영 이점: 작업과 검수 부담이 A의 약 1/3.
- 비용·리스크: period_cycle(0.73 vs 0.29)·sibling(0.82 vs 0.46) 격차가 남아 "사용자 질문 수준"이라고 하기 어렵다.

## Recommendation
**A.** 목표(사용자 질문 수준의 난도)에 닿는 것은 A뿐이다(계산상 ~0.31, C ~0.51, B ~0.48). 안전장치 (b)(c)로 셀 고정을 코드가 지키고, 목표를 v1 분포 구간으로 잡아 BM25에 맞춘 과적합을 막는다. 마감이 빠듯하면 C로 시작해 같은 코드로 나머지 유형을 이어 쓸 수 있다.
