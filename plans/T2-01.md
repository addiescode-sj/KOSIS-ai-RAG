# T2-01 메타데이터 수집

## Goal
- 완료 기준 (TASK.md 그대로): 약 2,364개 통계표의 표명·조사명·기관·수록기간·주기·분류·항목·링크 → `data/tables.jsonl`
- Linear KOS-24 (Urgent, 마감 10/29, 담당 임도유). T2-02 검색 골든셋, T2-04 BM25, T2-05 임베딩, T2-14 기간·주기 필터가 이 결과를 기다린다.
- Baseline (`data/tables.csv`, 2,364행): 8개 필드 중 표명·조사명·기관·수록기간(문자열)·링크 **5/8**. 주기·분류·항목은 **0/2,364표**. 수록기간은 목록 문자열("년 (2015 ~ 2025)")뿐이라 기간 필터에 바로 쓸 수 없다.

## 이미 있는 원천 (제공 데이터, 레포 밖 `data/`)

| 원천 | 건수 | 담긴 것 |
| --- | --- | --- |
| `data/tables.csv` | 2,364 | 표명, 조사명, 기관, 목록 수록기간, 수집 상태(A 2,348 / B 15 / C 1), 빠진 시점, 링크, 메뉴 경로 |
| `data/reference/population_table_catalog.jsonl` | 2,364 | 주제, 출처 문구, 주기별 수록기간(`catalog_periods`: 주기 라벨·시작·끝), 메뉴 경로 여러 개 |
| `data/table_metadata/<org>_<tbl>.json` | 2,364 | KOSIS 통계표 메타: 영문 표명, 단위, 수록 주기(`periodStr`, `containPeriod`), 분류명(`classInfoList`), 항목(`itemInfo`), 갱신일 |
| `data/values/<org>_<tbl>.parquet` | 2,364 | 실제 값. `prd_se`·`period`, 분류 라벨 `dimN_name/label`, `item_name` |

실측으로 확인한 것:
- **분류 라벨은 메타 JSON에 다 없다.** 선언된 라벨 수(`itmCnt`) 합계 550,745개 중 `itmList`에 실린 것은 86,417개(16%)다. 2,327개 분류가 잘려 있다. 지역명 질의("서울 출생아")가 검색에 걸리려면 라벨 전체를 Parquet에서 가져와야 한다.
- **주기 표기가 원천마다 다르다.** 메타 `periodStr`는 `F`(다년)가 1,921표다. 앞 300표에서 메타 `F`인데 Parquet `prd_se`는 `Y`인 표가 91개였다. 열어 보니 `containPeriod = "5년 1995 ~ 1995"`처럼 **5년 주기 조사의 한 시점만 있는 표**다. 메타가 틀린 게 아니라 Parquet이 연 단위 코드로 적은 것이다. 그래서 메타 주기(조사 주기)와 실제 시점 목록을 **둘 다** 남겨야 한다(리뷰 2). 하나로 덮으면 T2-14의 "인구총조사 5년 주기" 규칙이 깨진다.
- 읽기 속도: 가장 큰 Parquet(169MB)의 `prd_se`·`period` 두 칼럼 읽기 0.6초.
- 이름 충돌: `kosis_chat/data/schema.py`에 이미 dataclass `TableMeta`가 있다 → 새 모델 이름은 `TableRecord`로 한다.

이번 작업은 KOSIS API를 새로 부르는 수집이 아니라, 이미 받은 원천 네 개를 **표 하나당 한 줄로 합치고 원천끼리 대조하는 것**이다. T0-02(API 연결)는 제공 데이터로 대체되어 막힘이 아니다.

## `TableRecord` 필드 (모든 옵션 공통, 리뷰 5·6 반영)

`src/kosis_rag/schemas.py`(실전 2 스키마)에 둔다. 실전 1 `kosis_ai.schemas.TableInfo`(tables.csv 한 행)를 import해 필드로 감싸 key·표명·조사명·기관·링크·수집 상태를 한 곳에서 가져온다. 기존 계약은 바뀌지 않는다.

| 필드 | 형식 | 원천 | 쓰는 곳 |
| --- | --- | --- | --- |
| `info` | `TableInfo` | tables.csv | key(`<org>_<tbl>`), 표명, 조사명, 기관, 링크, 수집 상태, 빠진 시점 |
| `table_name_en`, `topic`, `menu_paths` | str, str, list[str] | 메타·catalog | 검색 문서 |
| `unit` | str \| None | 기존 `normalize._meta_unit` 재사용 | 답변·검색 |
| `cycle` | list[str] | 메타 `periodStr` (예: `["F"]`, `["M","Q","Y"]`) + `containPeriod` 문자열 | T2-14 조사 주기 |
| `prd_se` | list[str] | Parquet 고유값 | 실제 시점 코드 |
| `periods` | list[str] | Parquet 고유값, 정렬 | T2-14·답 없음 판정 |
| `start`, `end` | int (연도) | `periods`에서 계산 | T2-14 범위 비교 |
| `items` | list[str] | Parquet `item_name` 고유값 | 검색 |
| `classes` | list[{`name`, `labels`, `n_labels`}] | Parquet `dimN_name/label` 고유값 | 검색(지역명·연령 등) |
| `search_text` | str | 위 필드를 이어 붙인 한 문자열 | T2-04 BM25, T2-05 임베딩 문서 |
| `issues` | list[str] | 원천 대조 결과 (예: `period_outside_listed`, `labels_truncated_in_meta`) | 검증 리포트 |

- 리스트 필드는 Chroma 메타데이터(스칼라)에 그대로 못 넣는다. 평탄화 규칙은 T2-05에서 정하고, 여기서는 `search_text`와 스칼라(`start`, `end`, `unit`)를 함께 둔다.

## Idea
1. 빌더 `src/kosis_rag/metadata.py`: `build_records(data_dir) -> Iterator[TableRecord]` + CLI(`python -m kosis_rag.metadata --data-dir <data> --out data/tables.jsonl`). 경로 기본값은 이 레포의 `data/`. 단위는 실전 1 `kosis_ai.normalize._meta_unit`을 import한다(vendor 수정 없음).
2. 출력 `data/tables.jsonl`은 `/data/`가 gitignore라 레포에 들어가지 않는다(보안 서약). 팀에는 공유본으로 전달한다. 레포에는 코드·스키마·테스트·건수 리포트만 넣는다.
3. 리포트 `docs/reports/t2-01-metadata.md`: 필드별 채움률, 원천 간 불일치 건수(유형별), 파일 크기, 실행 시간. 표 내용(값)은 넣지 않는다.

## Option A — 목록 + 메타 JSON만 (Parquet 안 읽음)
- 접근: tables.csv + catalog + 메타 JSON. 기간은 `catalog_periods`·`containPeriod`, 분류 라벨은 메타 `itmList`(잘린 그대로), 항목은 `itemInfo`.
- 예상 성능 향상: 8개 필드 채움 5/8 → 8/8 표기상. 하지만 분류 라벨은 550,745개 중 86,417개(16%)만 들어가고, 실제 시점 목록이 없다. 실행 수 초.
- 실질 반영 이점: T2-02·T2-04가 바로 시작할 수 있다.
- 비용·리스크: 2~3시간. 지역·연령 라벨 84%가 빠져 BM25가 라벨 질의를 못 찾는다. 수집 누락(B·C 16표)의 실제 시점을 모른다.

## Option B — 원천 우선 + Parquet 고유값으로 확정 (추천)
- 접근: A의 원천을 먼저 쓰고(리뷰 4), Parquet에서는 `prd_se`·`period`·`item_name`·`dimN_name/label`의 **고유값만** 읽어 실제 시점·항목·분류 라벨을 채운다. 메타 주기는 `cycle`, 실제 시점은 `periods`로 따로 둔다. 원천끼리 다르면 `issues`에 남긴다.
- 예상 성능 향상: 8개 필드 8/8, 분류 라벨 16% → 100%(Parquet 기준), 실제 시점 목록 0 → 2,364표. 원천 간 불일치를 유형별 건수로 처음 측정한다. 실행 시간은 전체 실행으로 측정해 리포트에 적는다(가장 큰 표 기간 칼럼 0.6초 실측, 라벨 칼럼은 미측정).
- 실질 반영 이점: 데이터 정확성(1순위). T2-14와 실전 2의 "없는 연도" 판정이 실제 시점을 쓴다. 실전 1 판정과 같은 원천(Parquet)이라 두 단계가 어긋나지 않는다.
- 비용·리스크: 반나절. 라벨 칼럼이 큰 표에서 느릴 수 있다 → 칼럼별 고유값만, 표 하나씩 처리. `tables.jsonl` 크기가 커질 수 있다(라벨 55만 개) → 리포트에 크기를 적고, 검색 쪽에서 필요하면 자른다.

## Option C — B + KOSIS OpenAPI로 주석·설명자료 추가 수집
- 접근: B에 더해 KOSIS OpenAPI로 통계표 주석·용어 설명(`existCmmtKor = Y`)을 받아 붙인다.
- 예상 성능 향상: 개념어 질의(예: "주민등록 총인구수") 재현율 상승 기대. T2-02·T2-04 기준선이 없어 지금은 측정할 수 없다.
- 실질 반영 이점: T2-05 임베딩 문서가 풍부해진다.
- 비용·리스크: 하루 이상. API 키·호출 제한·네트워크 필요, T0-02 미완료. 보안 서약상 제공 범위 밖 수집인지 팀 확인 필요. 마감(10/29) 리스크가 크다.

## Recommendation
**옵션 B.** 메타 JSON만으로는 분류 라벨의 84%가 빠지고 실제 시점이 없어서, 검색(T2-04)과 기간 필터(T2-14)가 둘 다 약해진다. B는 반나절에 원천 우선 + Parquet 고유값으로 이를 채우고, 원천 간 차이를 숫자로 남긴다. C는 기준선이 생긴 뒤(T2-04 결과) 필요하면 별도 태스크로 한다.
