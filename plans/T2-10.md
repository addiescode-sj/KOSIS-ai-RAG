# T2-10 검색 파이프라인 LangGraph 노드화 (1차)

## Goal
- 완료 기준 (TASK.md 그대로): 검색 API 고정 (산출물①) — `search_tables(question, k) -> list[TableCandidate]` (후보 + 점수)
- 이번 범위 (사용자 지시, `NODE_TASK_GUIDE.md` 11/03): 지금 검색은 LangChain 검색기를 겹겹이 감싼 구조다
  (`HybridRetriever`(+조건) → `CrossEncoderReranker`(1단계) → `LLMReranker`(2단계)). 각 단계가 안에서 `base.invoke()`로 앞 단계를 부르고,
  `chain.answer()`가 거절 / LLM 안내 / 템플릿 대체 분기를 함수 하나에 담고 있다. 이를 LangGraph `StateGraph`로 바꾼다.
  각 단계는 공유 상태를 읽고 쓰는 노드 하나가 되고, 분기는 조건부 엣지가 된다. **동작은 바꾸지 않는다.**
  순서, `Document.metadata` 키와 값, `SearchResult` 필드, 예외가 모두 기존과 같아야 한다.
- 이번 작업만으로 T2-10을 완료하지 않는다 (사용자 결정 11/03). `tools.search_tables`를 그래프로 옮기는 일과 API 고정은 남은 일로 Result에 적는다.
- Baseline: 지표 변화가 목표가 아니다. 기준선은 **같은 환경에서 기존 경로로 돌린 L1 실행**이다 (Measure 참조).
  기존 오프라인 테스트가 모두 통과하는 상태가 시작점이다 (사용자 실행 결과로 기록).

## Idea
1. **함수 분리 (동작 변경 없음)**: 각 래퍼 클래스의 계산을 "문서 목록 → 문서 목록" 순수 함수로 꺼낸다. 클래스는 그 함수를 부르는 얇은 껍데기로 남긴다.
   - `retriever.hybrid_search(query, retrievers, *, names, table_filter, records, k, k_each, c, score_from) -> (docs, removed)`
     — `HybridRetriever._lists` + `_get_relevant_documents` 본문. 필터는 `self.condition(query)` 대신 인자로 받는다.
   - `rerank.rerank_stage1(query, docs, score, *, n, mode, c)`, `rerank.rerank_stage2(query, docs, select, *, k_in, name)`
     — 두 리랭커의 본문에서 `self.base.invoke(query)`만 뺀 것.
   - `chain.decide_route(docs) -> (route, reason)`, `chain.refusal_answer(question, docs, reason)`, `chain.guide_answer(question, docs, client)`
     — `answer()`를 세 함수로 나누고, `answer()`는 이 셋을 불러 지금과 같은 결과를 낸다.
   - `pipeline.SearchResources` + `load_resources(...)` — `build_search`의 로딩(레코드·Chroma·BM25·텍스트 형식·1단계 점수기·2단계 선택기)을 배선과 분리한다.
     `build_search`는 시그니처를 유지하고 `load_resources` 결과로 지금과 같은 순서로 감싼다.
     2단계 이름 규칙(`select`가 주입되고 `STAGE2`가 꺼져 있으면 `"custom"`)과 BM25 `k` 규칙(조건 필터가 켜져 있으면 전체 레코드 수, 아니면 `pool`)을 그대로 옮긴다.
2. **그래프 (`src/kosis_rag/graph.py`, 신규)**:
   - 상태: Pydantic `SearchState`(question, query, removed, docs, route, refusal_reason, result, trace).
   - 노드 7개: `parse` → `retrieve` → [`rerank1`] → [`rerank2`] → `gate` → `refuse` | `guide`.
   - 단계 생략은 그래프를 만들 때 노드를 넣고 빼서 정한다. 런타임 조건부 엣지는 `gate` 하나뿐이다.
   - `retrieve`는 `parse`가 만든 `ParsedQuery.to_filter()`를 `hybrid_search`에 넘긴다. 질문을 두 번 파싱하지 않는다.
     `parse_query`는 `kosis_rag.query` 모듈을 통해 부르므로, 테스트에서 패치해 호출 횟수를 셀 수 있다.
   - 조건 필터가 꺼져 있으면(`cond_filter` off, 프리셋 `hybrid`) `parse`는 실행되지만 `retrieve`는 필터 없이 검색한다 (`pipeline.py:119`와 같음).
   - `k`(답변에 보이는 후보 수)는 `gate`·`refuse`·`guide`에서만 자른다(`docs[:k]`, `chain.py:116`과 같음). `state.docs`는 자르지 않아서 L1이 Hit@10까지 볼 수 있다.
   - `HybridRetriever.last_removed` 속성은 남긴다 (`tests/test_staged_search.py:139`가 읽음). 그래프에서는 `state.removed`로 같은 값을 낸다.
   - 공개 함수: `build_graph(resources, client, *, k=5)`, `run_search(graph, question) -> SearchState`.
   - `langgraph`는 `graph.py`에서만 import한다. 기존 경로는 langgraph 없이도 동작한다.
3. **docstring (사용자 요구)**: 추가·수정한 함수와 클래스 전부, 그리고 그래프 노드가 직접 부르는 기존 함수에 영어 docstring을 붙인다.
   - 기존 함수 목록: `parse_query`, `TableFilter.is_empty`, `filter_tables`, `why_excluded`, `soft_rank`, `blend_order`, `passage_scorer`, `format_context`, `llm_runnable`, `unsupported_claims`, `template_answer`, `with_citations`, `to_candidate`, `read_records`, `bm25_text`, `text_format`
   - 형식: Does / In / Out / Side effects / Node. 기존 docstring 문구, 태스크 ID, `ponytail:`, `TODO`는 지우지 않는다.
4. **의존성**: `pyproject.toml`과 `requirements.txt`에 `langgraph>=1.0,<2`를 추가한다. `uv.lock`은 직접 고치지 않고 사용자가 `uv lock`으로 갱신한다.
5. **evals 측정 경로 (evals 담당자 승인 11/03)**: `evals/runners/retrieval.py`의 `build()`가 `graph:<STAGED 프리셋 이름>`을 받게 한다.
   - 설정은 같은 `STAGED` 표를 쓰고, 실행만 그래프로 한다. 러너는 `invoke(q, config={"callbacks": ...})[:k]`를 부르고 metadata를 읽는다(`runners/retrieval.py:86-102`).
     그래서 그래프를 `RunnableLambda`로 감싸 `config`를 `graph.invoke`에 그대로 넘기고, 자르지 않은 `state.docs`를 돌려준다. 예외 처리(try/except)는 러너의 기존 코드가 맡는다.
   - 안내 문장 단계는 LLM을 부르지 않도록 실전 1 `MockClient`(오프라인)를 넣는다. 네트워크 호출이 없고, LangChain LLM 콜백에도 잡히지 않으므로 호출·토큰 수가 늘지 않는다. L1은 표 목록만 채점하므로 지표에 영향이 없다.
     지연(`latency_ms`)에는 템플릿 생성 시간 몇 ms가 더해지지만, 지연은 일치 기준이 아니다.
   - 기존 프리셋과 채점기, 리포트는 바꾸지 않는다.
6. **테스트 (`tests/test_graph.py`, 신규, 오프라인)**: 지침서 6단계 그대로다.
   - 함수 분리 동등성: hybrid, 1단계 두 모드, 2단계 4가지 경우
   - 그래프 vs `chain.answer(build_search(...))` 동등성: 사례 a~j
   - 그래프 모양: 켜진 단계에 따른 노드 집합
   - parse 1회 호출
   - 기존 테스트 파일은 고치지 않는다.

## Option A — 함수 분리 + 그래프 v1 (지침서안)
- 접근: Idea 1~6. 각 단계를 순수 함수로 꺼내 기존 클래스와 그래프가 같은 함수를 공유한다.
- 예상 성능 향상: 검색·답 없음 지표 변화 **0이 목표**다. Hit@1/5/10, MRR, 답 없음 P/R/F1, 문항별 상위 표 순서가 기존 경로와 100% 같아야 한다.
  지연은 노드 사이 Pydantic 상태 검증 몇 ms가 늘 수 있지만, 질문당 초 단위인 검색·LLM 시간에 비하면 무시할 수준이라고 가정한다(실측으로 확인, `ops.json` p50).
- 실질 반영 이점:
  - 기술 설계: 단계별 입출력이 상태(`query`, `removed`, `docs`, `route`, `trace`)로 드러난다. 검색기 객체에 쓰던 `last_removed`/`last_query` 부작용 없이도 필터 제외 사유와 단계별 시간을 볼 수 있다.
  - 예외 처리: 거절 분기가 `gate` 엣지로 드러나 실패 분석(T2-13)에서 어느 노드에서 거절했는지 읽을 수 있다.
  - 재사용: 종합 단계 에이전트(LangGraph)가 이 그래프를 서브그래프나 툴로 그대로 쓴다. 노드 함수는 기존 클래스와 공유되므로 코드가 두 벌이 되지 않는다.
- 비용·리스크: 1~1.5일. 파일 6개 수정, 2개 신규. 리팩터링 중 동작이 바뀔 위험은 동등성 테스트(사례 a~j)와 실제 데이터 L1 비교로 막는다.

## Option B — 기존 검색기 객체를 블랙박스 노드로 감싸기 (분리 없음)
- 접근: `build_search`가 만든 검색기 사슬을 노드 하나로, `chain.answer`를 노드 하나로 감싼다.
- 예상 성능 향상: 지표 변화 0. 코드 변경이 가장 적다.
- 실질 반영 이점: "LangGraph를 쓴다"는 형식만 갖춘다. 단계가 여전히 클래스 안에 묶여 있어 노드끼리 상태를 나눌 수 없다. 필터 제외 사유·파싱 결과·단계별 시간이 상태에 드러나지 않는다.
- 비용·리스크: 0.5일. 노드화 목적(단계 분리, 상태 공유)을 이루지 못한다. **기각.**

## Option C — A + 실전 1 `summarize_stat` 노드
- 접근: A에 `guide` 다음 수치 답변 노드(`summarize_stat(question, top1)`)를 더해 검색 → 수치 답까지 한 그래프로 만든다.
- 예상 성능 향상: e2e(L4) 경로를 그래프로 측정할 수 있다. 검색 지표 변화는 0이다.
- 실질 반영 이점: 종합 단계 구조를 먼저 갖춘다.
- 비용·리스크: +1일 이상. 실전 1 내부 API(span 미노출, `api._build` 우회)에 의존한다. 지침서 범위 밖이고 오늘 마감(11/03)을 넘긴다. **이번 범위 아님.**

## Recommendation
옵션 A. 실질적인 선택지는 A 하나다. B는 노드화 목적(단계 분리, 상태 공유)을 이루지 못해 기각하는 안이고, C는 A의 범위 확장이다.
