# T2-38 안내 답변 토큰 스트리밍 (백엔드 SSE → 채팅 화면)

## Goal
- 완료 기준 (TASK.md 그대로): guide 노드의 LLM 답변을 토큰 단위로 `/search/stream`에 흘리고(T2-37), 채팅 화면(T2-11)이 받아 그린다.
  검증(`unsupported_claims`)·템플릿 대체·출처 부착 규칙은 그대로이고, 최종 `SearchResult`는 `run_search`와 같다(pytest).
- 배경: T2-37 옵션 C로 검토했다가 "검증 전 문장이 화면에 먼저 나간다"는 이유로 미뤘다. 이번엔 그 문제를 푸는 방식을 고른다.
- Baseline: 답변 문장은 guide 노드가 끝난 뒤 `event: result`로 한 번에 온다 → 사용자가 첫 글자를 보는 시간 = 검색 + guide LLM 전체 생성 시간.
  로컬(mock LLM)에서 guide 0.5 ms라 실측 의미 없음. 실제 HCX 안내 생성 시간은 이 레포에 측정값 없음 → 사용자 실행으로 잰다.

## Idea
1. **같은 노드, 같은 결과** — 스트림을 도는 코드는 `chain.guide_answer` 안에 둔다(필터에 question·candidates가 필요, 리뷰 2).
   `guide_answer(question, docs, client, on_text=None)`: `BaseChatModel`이면 `(PROMPT | client).stream(...)`의 청크를 이어 붙이며
   매 청크 뒤 `on_text(새로 안전해진 부분)`을 부르고, Phase 1 `LLMClient`(`MockClient`, `.stream` 없음)는 지금처럼 `generate` 한 번.
   스트림 도중 예외는 반복문 전체를 try로 감싸 지금처럼 `STATUS_API_ERROR` → 템플릿. 끝나면 **이어 붙인 전체 문장으로 지금과 같은**
   NO_MATCH·검증·템플릿·출처 판정 → `SearchResult`가 구조적으로 같다.
2. **안전한 앞부분 = 순수 함수 하나** (리뷰 5) — `safe_prefix(text, question, candidates) -> str`:
   - lstrip한 누적 텍스트가 `NO_MATCH`의 앞부분이거나 같으면 `""` (스트림이 끝날 때까지 보류, "NO_MATCH\n"도 막음, 리뷰 2)
   - 아니면 마지막 공백 이전까지 자르고, 그 부분에 `unsupported_claims`가 하나라도 있으면 그 직전까지(이후 전송 중단)
   - guide_answer는 `safe_prefix`가 이전보다 길어진 만큼만 `on_text`로 보낸다.
3. **검증 정규식 보강** (리뷰 1) — `_TBL_ID = \bDT_…`는 한글 바로 뒤("표DT_1B04005N")에서 `\b`가 성립하지 않아 안 잡힌다(지금도 있는 구멍).
   `(?<![0-9A-Za-z_])DT_[0-9A-Za-z_]+`로 바꾸고 pytest로 고정. 스트리밍과 별개로 템플릿 대체가 조금 늘 수 있다 → 기존 chain·graph 테스트로 회귀 확인.
4. **노드 밖으로 토큰 내보내기** — guide 노드에서 `get_stream_writer()`를 try로 얻어(그래프 밖 `/nodes/answer`·`chain.answer`에선 RuntimeError → None, 리뷰 3)
   `on_text=lambda d: writer({"delta": d})`. `graph.stream_search`는 `stream_mode=["updates","values","custom"]`로 `("token", {"delta"})`를 낸다.
   API는 `event: token`. `run_search`(invoke)에선 writer가 아무 일도 안 한다(11/03 시험 확인).
5. **사용량** (리뷰 4) — ChatClovaX(`BaseChatOpenAI`)는 기본 URL이 아니라 `stream_usage`가 꺼져 있어 `.stream` 청크에 `usage_metadata`가 없다
   → `clova_chat()`에 `stream_usage=True`, 청크 합으로 `LLMResult.usage`. HCX가 `stream_options`를 받는지는 실제 호출로만 확인 가능(사용자 실행).
6. **화면** — Route Handler가 `event: token`을 AI SDK `data-draft` part(같은 id로 누적 텍스트 갱신)로, `event: result`의 최종 답변을 text part로.
   text part가 오기 전까지 draft를 "작성 중"으로 보여 주고, 결과가 오면 최종 문장(검증·출처 포함)으로 바꾼다. 템플릿으로 바뀌면 "검증 실패로 코드 안내" 배지.

## Option A — 원문 토큰 즉시 전송 (초안 표시)
- 접근: LLM 토큰을 받는 대로 모두 `event: token`. 검증은 끝에서만. 화면은 "초안"으로 표시하고 결과로 교체.
- 예상 성능 향상: 첫 글자 시간 = 검색 + LLM 첫 토큰. HCX 첫 토큰 시간은 **측정값 없음**(추정: 생성 전체보다 짧음). 전체 시간은 같다.
- 실질 반영 이점: 응답 품질 체감 최대. 구현 가장 단순(필터 없음).
- 비용·리스크: 반나절. **후보에 없는 표 ID·연도가 초안으로 화면에 잠깐 보인다** — 템플릿으로 바뀌어도 사용자가 이미 봤다.
  `NO_MATCH`도 글자로 흘렀다가 거절 문장으로 바뀐다. 데이터 정확성(평가 1순위) 원칙과 충돌.

## Option B — 검증된 앞부분만 전송 (단어 경계 검증)
- 접근: 토큰을 모으되, 마지막 공백 이전까지(끝이 잘린 단어 `DT_1B0…`·`202…`는 보류)를 `unsupported_claims`로 검사해 통과한 부분만 보낸다.
  검사는 앞부분 단조성에 기대어 맞다: 앞부분에서 걸린 ID·연도는 전체 문장에서도 걸린다(정규식이 단어 단위, 공백에서 끊김).
  처음 걸리는 순간 전송을 멈춘다 → 최종은 템플릿(지금과 같음). 지금까지 쓴 글자가 `NO_MATCH`의 앞부분이면 보류.
- 예상 성능 향상: 첫 글자 시간 = 검색 + 첫 단어 도착(A + 단어 하나 분량의 토큰, **측정값 없음**). 검증 실패 시엔 멈춘 뒤 결과까지 대기(지금과 같음).
- 실질 반영 이점: 화면에 나가는 글자는 모두 검증을 통과한 것 → 데이터 정확성 유지 + 스트리밍 체감. 검증 규칙이 하나(`unsupported_claims`)라
  스트리밍용 규칙이 따로 생기지 않는다. 종합 단계 에이전트 답변에도 같은 필터를 쓸 수 있다.
- 비용·리스크: 반나절~1일 (필터는 순수 함수 하나, 결과는 전체 텍스트로 재계산). 앞부분 단조성은 공백 경계에서 성립(리뷰 1 확인), 한글 인접 ID는 정규식 보강으로.
  검증에 실패하면 이미 보인 앞부분(검증 통과분)이 템플릿으로 바뀐다 → 화면에 "검증 실패로 코드 안내로 대체" 표시.

## Option C — 검증 후 재생 (LLM 스트리밍 없음)
- 접근: guide 노드는 그대로(invoke). 결과가 나온 뒤 검증된 최종 답변을 백엔드가 몇 글자씩 `event: token`으로 나눠 보낸다(타자 효과).
- 예상 성능 향상: 첫 글자 시간 변화 없음(LLM 전체 생성 뒤). 체감만 "흘러나오는" 모양.
- 실질 반영 이점: 위험 0, 노드·체인 변경 0. 화면 연결(draft part)만 연습.
- 비용·리스크: 반나절. 요청한 "토큰 단위로 흘려보내기"의 실익(기다림 감소)이 없다 — 발표에서 실측하면 전후 같은 수치.

## Recommendation
**Option B.** 첫 글자 시간을 실제로 줄이면서(A와 단어 하나 차이) 화면에 검증 안 된 표 ID·연도가 나가지 않는다.
A는 정확성 원칙과 충돌하고, C는 지연이 줄지 않는다.

## Measure
1. 결과 동일 (pytest, 스트리밍 가짜 모델 `GenericFakeChatModel`): 토큰을 흘린 `stream_search` 결과 = `run_search` = `chain.answer` — guide·NO_MATCH·템플릿 대체 세 경로.
2. 안전성 (pytest): 흘려보낸 토큰을 이어 붙인 문자열에 `unsupported_claims`가 비어 있음, `NO_MATCH`(·"NO_MATCH\n")는 한 글자도 안 나감,
   실패 시 전송 중단, 한글 인접 ID("표DT_X") 검출, `/nodes/answer`(그래프 밖)·`chain.answer` 동작 유지, 청크 usage 합산.
3. 지연 (사용자 실행, 실제 HCX): 질문 N개로 첫 `event: token` 시간 vs `event: result` 시간 — 전 = result 시간, 후 = 첫 token 시간.

## Result
구현 (옵션 B, 2026-11-03):
- `chain.py`: `llm_runnable(client, on_chunk)` — chat model을 `.stream`으로 받아 청크 합(텍스트·`usage_metadata`), 스트림 도중 예외도 `STATUS_API_ERROR`.
  `streamable_prefix()` — 마지막 공백까지, NO_MATCH 앞부분/전체면 `""`, 검증 실패면 `None`(전송 중단). `guide_answer(..., on_text)` — 늘어난 만큼만 전송,
  최종 판정은 전체 텍스트로 지금과 같음. `_TBL_ID` 보강(`(?<![0-9A-Za-z_])DT_`, 한글 뒤 ID 검출). `clova_chat()`에 `stream_usage=True`.
- `graph.py`: guide 노드가 `get_stream_writer()`(그래프 밖이면 None)로 `{"delta"}` 전송, `stream_search`에 `custom` 모드 → `("token", ...)`.
- API: `/search/stream`에 `event: token` (Swagger 설명·`docs/openapi.json` 갱신). 프론트: `data-draft` part(같은 id 갱신)로 "작성 중" 카드,
  결과가 오면 최종 문장으로 교체, 템플릿 대체 시 배지.
