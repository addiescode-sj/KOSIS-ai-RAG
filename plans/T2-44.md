# T2-44 벡터 저장소 Chroma → PostgreSQL + pgvector (Linear KOS-138)

배경·현황·검토 내용은 종합 저장소 `plans/T3-47.md`에 있다. 이 문서는 실전 2 저장소에서 바꿀 것만 적는다.

## Goal
- 완료 기준 (TASK.md 그대로): 컬렉션별 개수·벡터 일치, L1 골든 parity(master Chroma vs 브랜치 pgvector) 순위 동일,
  조건 필터 결과 개수, dense 지연 전→후, pytest.
- 기준선: master `f569721` + Chroma 1.5.9 볼륨(컬렉션 9개). 수치는 데이터(볼륨) 수령 후 `## Result`에 기록.

## 바꾸는 방식 (공통)
검색·적재 코드가 Chroma에 바라는 기능은 적다.

| 기능 | 쓰는 곳 |
|---|---|
| `get_collection(name, embedding_function=None)` · `.metadata` · `.count()` · `.name` | `legacy/retrievers.py` |
| `.query(query_embeddings, n_results, include, where={"key": {"$in": [...]}})` | `retrieve/dense.py`, `retrieve/hq.py` |
| `get_or_create_collection` · `.modify` · `get_max_batch_size` · `.upsert` · `.get(include=[])` · `.delete(ids)` | `kosis_rag_build/chroma.py` `load` (chunks·hq-index도 이 함수) |
| `list_collections` | `chroma --list` |

그래서 `adapters/vectorstore.py`에 **같은 메서드를 가진 pgvector 클라이언트**를 두고, 위 호출 코드는 그대로 둔다.
`where`는 `key $in`만 지원한다(그 밖의 조건은 ValueError). `scripts/check_build.py`의 `$and/$or/$contains` 진단은 Python 쪽 확인으로 바꾼다.

테이블(어댑터 `ensure_schema()`가 `IF NOT EXISTS`로 만든다. 종합 저장소는 alembic `0002_pgvector`가 같은 정의로 먼저 만든다):

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE IF NOT EXISTS vector_collection (name text PRIMARY KEY, metadata jsonb NOT NULL, created_at timestamptz NOT NULL DEFAULT now());
CREATE TABLE IF NOT EXISTS vector_item (
  collection text NOT NULL REFERENCES vector_collection(name) ON DELETE CASCADE,
  id text NOT NULL, key text, document text NOT NULL, metadata jsonb NOT NULL, embedding vector NOT NULL,
  PRIMARY KEY (collection, id));
CREATE INDEX IF NOT EXISTS vector_item_key ON vector_item (collection, key);
```

- 차원은 컬렉션 메타데이터 `dim`으로 확인한다(넣을 때 길이가 다르면 ValueError). 열은 차원을 고정하지 않는다(컬렉션마다 다를 수 있음).
- 벡터 인덱스(HNSW)는 두지 않는다: 2,364 · 5,158행은 전체 비교가 빠르고, 조건 필터 뒤 결과가 줄지 않는다.
- 점수 = `1 - (embedding <=> q)` (Chroma cosine distance와 같은 뜻). 같은 거리면 id 순으로 정렬해 결과를 고정한다.

## Option A — Chroma를 빼고 pgvector 하나로 (선택)
- 이름 변경(깨는 변경, 종합 저장소도 같이 고침):
  `ChromaConfig(host, port, collection)` → `VectorStoreConfig(url, collection)` · `IndexSpec.chroma` → `IndexSpec.vector_store` ·
  `ChromaTableRetriever` → `DenseTableRetriever` · `adapters.chroma.chroma_client` → `adapters.vectorstore.vector_client` ·
  빌드 모듈 `kosis_rag_build.chroma` → `kosis_rag_build.vectors`, 명령 `chroma` → `vectors`, `--chroma-host/--chroma-port` → `--database-url` ·
  환경변수 `CHROMA_HOST/CHROMA_PORT` → `DATABASE_URL`, `CHROMA_COLLECTION` → `VECTOR_COLLECTION`. 컬렉션 이름 규칙은 그대로.
- compose: `chroma` 서비스 → `postgres`(`pgvector/pgvector:0.8.1-pg17`, 호스트 5432는 127.0.0.1에만).
- 의존성: `chromadb-client` → 기본에서 빼고 `[dependency-groups] migrate`에만. `psycopg[binary]`·`pgvector` 추가.
- `scripts/chroma_to_pgvector.py`: 로컬 Chroma의 컬렉션을 벡터 그대로 옮기고 개수·id·벡터를 대조.
- parity: `scripts/parity_l1.py` compare에 `--score-tol`, fingerprint에 `store`(compare에서 `--ignore-config store`).
- 예상 수치: L1 Hit@1/5/10·MRR 변화 없음(같은 벡터, 정확 검색), 조건 필터 결과 개수 같거나 많음, 컨테이너 1개 감소.
- 비용·리스크: 팀원 로컬 환경이 한 번 바뀐다(이전 명령 1개로 해결). 되돌리려면 이 PR을 되돌린다.

## Option B — 설정으로 두 저장소를 고르게
- `VECTOR_STORE=chroma|pgvector` 분기. 되돌리기 쉽지만 QA 기간 동안 두 코드가 공존하고 정리를 따로 해야 한다.

## Option C — 검색을 SQL로 다시 짠다
- 등록부 필터·BM25까지 DB로. 검색 수치가 움직일 수 있고 일정에 맞지 않는다. 범위 밖.
