# T2-09 답 없음 판정 (HCX-007 LLM 리랭커)

## Goal
- 완료 기준 (TASK.md 그대로): HCX-007 LLM 리랭커(2차, T2-07 `LLM_RERANKERS`)가 고른 표가 없으면 답 없음, 점수 임계값과 골든셋으로 비교·보정, 범위 밖(지역통계 등) 안내 문구. 완료 기준: 리랭커 전/후 · thinking_effort none/low의 답 없음 P/R/F1(사유별)·Hit@1·MRR·지연·호출 수 비교 리포트(`lab/`)
- 방향 변경 (11/02): 점수 임계값/분류기 대신 LLM 기반 리랭크(HCX-007)로 판정한다. 임계값 τ는 기준선과 보조 규칙으로 남긴다.
- Baseline (T2-07 Result, dev 39 = 답 있음 29 + 답 없음 10, n2 미세조정 가중치 기준 참고값):
  - hybrid+cond, τ 판정: Hit@1 13 · MRR 0.551 · 답 없음 F1 0.750 (`evals/reports/20261102-151721-T2-06-hybrid-cond`)
  - staged(1차), τ 판정: Hit@1 17 · MRR 0.656 · 답 없음 F1 0.737
  - 이 PC에는 미세조정 가중치(`data/models/`)가 없어서 위 수치를 그대로 재현할 수 없다. 측정 기준선은 같은 실행 환경에서 리랭커 없이 다시 잰다 (아래 "측정 환경").
- 골든셋 답 없음 문항: dev 10(범위 밖 5 · 기간 불일치 3 · 항목 없음 2), test 18(11 · 5 · 2). dev에서 1문항 = recall 0.1.

## Idea
1. T2-07이 만든 2차 자리(`rerank.LLMReranker` + `LLM_RERANKERS`)에 `"hcx"` 항목을 추가한다. HTTP는 실전 1 `kosis_chat.llm.model.HCXClient`(HCX-007 `thinking.effort`·`maxCompletionTokens`·재시도 지원)를 그대로 쓴다. 새 HTTP 코드 없음.
2. HCX-007에 질문 + 후보 상위 20개(번호, 표 텍스트)를 주고 JSON으로 고르게 한다. 번호는 입력에서만 매핑하므로 표 ID를 지어낼 수 없다 (T2-07과 같음).
3. `stage2_picked_n == 0`(오류 없이)을 답 없음 신호로 쓴다. 판정은 evals L1 러너가 τ 규칙과 나란히 채점하고, 서비스 경로(`chain.answer`)도 같은 신호로 거절한다. 이때 답변 LLM(HCX-DASH) 호출은 건너뛴다. 서비스에는 보정된 τ가 없으므로 τ 결합은 평가에서만 쓴다.
4. 기간 불일치(no_period)는 LLM에 맡기지 않는다. T2-14 조건 필터(코드)가 후보를 0건으로 만드는 경로를 그대로 쓴다 (CLAUDE.md: 기간·숫자 판단은 코드).
5. 공통 평가 수정 (옵션 무관):
   - 러너 행에 `stage2_picked_n`·`stage2_error`·`stage2_reason`·`stage2_calls`를 싣는다. 판정 규칙 `tau` · `llm`(picked 0, 오류 없음) · `either`(둘 중 하나)를 같은 실행에서 함께 채점한다.
   - **τ 공정성 수정**: 지금 `runners/retrieval.run()`은 재정렬 **뒤** `docs[0]`의 점수를 `top_score`로 쓴다. 그래서 리랭커 실행의 τ가 리랭커 없는 기준선과 다른 표를 본다 (T2-07 staged-clova F1 0.737 → 0.667 하락의 원인일 수 있음). 이를 1단계 기준 최고 점수(`max(score)`, 자르기 전 전체 목록)로 고친다.
6. 측정: 리랭커 없음(τ) vs HCX-007 thinking none vs low. 설정이 되면 CLOVA(`clova-only`)의 picked 0 F1도 새 HTTP 코드 없이 참고 기준선으로 잰다. dev로 프롬프트를 확정한 뒤 test로 공식 수치를 낸다. 결과는 `lab/T2-09-hcx-no-answer/REPORT.md`에 남긴다.

> 예상 수치는 모두 **실측 전 가설**이다. dev 답 없음은 10문항이라 옵션 간 1~2문항 차이는 노이즈 안이다. T2-07에서 LLM 2차를 붙였을 때 F1이 오히려 떨어진 전례(0.737 → 0.667, τ 측정 방식 영향 가능)가 있다. 지연도 근거가 없다(CLOVA만 써도 p95 54초). 그래서 test 18문항까지 합쳐 판단한다.

## Option A — 선택형: 고른 표 0개 = 답 없음 + 사유 라벨 (최소안)
- 접근: `"hcx"` 리랭커를 추가한다. 출력은 `{"picked": [번호...], "reason": "out_of_scope" | "no_item" | null}`(같은 호출, 필드 하나만 추가). 고른 표는 T2-07처럼 앞으로, 나머지는 1단계 순서. 거절 안내 문구는 코드가 고른다: 필터 0건 → 기간 불일치, 그 외에는 reason별 문구, reason이 없으면 `REFUSAL_TEXT`. `SearchResult.no_answer_reason` 추가.
- 예상 성능 향상 (가설): 답 없음 F1이 같은 1단계 τ 대비 +0.03~0.08(`llm` 또는 `either`). Hit@1 ±1. 근거: 범위 밖 16/28문항은 비인구·지역통계 주제라 LLM이 아무것도 안 고를 여지가 크다. 반면 과선택(비슷한 표를 고름)은 recall을 깎는다.
- 실질 반영 이점: 예외 처리(거절)와 응답 품질(사유별 안내). `STAGE2=hcx` 스위치로 T2-10 `search_tables`·종합 에이전트에 그대로 재사용할 수 있다. 규칙 ablation(τ/llm/either)이 "무엇을 바꿔서 몇 → 몇"을 분리한다.
- 비용·리스크: 1일(공통 평가 수정 포함). 질문당 HCX-007 1회 호출. reason 정확도는 dev 10문항으로만 맞춰 보므로 탐색적이다.

## Option B — 등급형: 표별 관련도 0~3 + 보정 임계값 (고성능안)
- 접근: HCX-007이 후보 20개 각각에 관련도 등급을 매기고 등급순(동률은 1단계 순서)으로 재정렬한다. 답 없음 = 최고 등급 < g*. g*는 dev에서 `best_tau`로 보정한다.
- 예상 성능 향상 (가설): 답 없음 F1 +0.05~0.10, Hit@1 +1~3. 근거: 등급이 "고름/안 고름"보다 정보가 많아 임계값을 보정할 수 있고, 전체를 재정렬하면 1위가 바뀔 수 있다.
- 실질 반영 이점: 검색 품질(Hit@1)과 거절을 한 번에 다룬다. 등급 분포가 실패 분석(T2-13) 자료가 된다.
- 비용·리스크: 1.5일. 출력 토큰이 크게 늘어 지연·비용이 커진다(thinking low면 더 큼). 20개 등급 JSON 파싱 실패율이 있다. 마감(11/03) 위험.

## Option C — 판정 전용: 1단계 상위 5개에 대한 답변 가능성 판정, 재정렬 없음 (저비용안)
- 접근: 순서는 건드리지 않고 HCX-007에 상위 5개만 주어 `{"answerable": bool, "reason": ...}`만 받는다. `LLMReranker` 대신 같은 자리에 판정 단계를 하나 둔다.
- 예상 성능 향상 (가설): 답 없음 F1은 A와 비슷하고 Hit@1은 변화 없음(재정렬이 없으므로). 입력이 1/4 수준이라 지연·토큰이 가장 적다.
- 실질 반영 이점: 거절만 싸게 개선. 다만 "LLM 리랭크로 구현" 방향(11/02 결정)과 맞지 않는다.
- 비용·리스크: 반나절~1일. 상위 5개에 정답이 없지만 6~20위에 있는 문항은 오거절한다.

## Recommendation
