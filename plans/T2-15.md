# T2-15 OpenTelemetry 계측 설계 (+ Jaeger, 실패 단계 리포트)

## Goal
- 완료 기준 (TASK.md 그대로): 반나절 작업. T1-22 단계별 로그를 span으로 옮기는 설계(검색 단계를 포함한 span 단위·속성)를 정리한다. LLM 토큰·비용은 Jaeger가 아니라 OpenTelemetry에서 별도로 계측한다. 도구는 OpenTelemetry + Jaeger로 확정됨
- 사용자 요청(10/31, KOS-67): 설계만이 아니라 계측 코드까지. 실패한 문항이 **어느 trace·span(단계)에서, 어떤 원인으로** 실패했는지 —
  질문 이해 실패 / 숫자 계산 모듈을 건너뜀 / 도구 호출 실패 / 어떤 도구를 불렀는지 — 를 `report.md`와 `report.html`에 표시한다.
- Baseline:
  - 단계 관측: Phase 1 `StatPipeline.ask`가 OTel 모양 span dict를 `decision_metadata["spans"]`에 남긴다(T1-22, 7단계).
    그러나 `summarize_stat`은 `StatAnswer`만 돌려줘 **evals 실시간 실행(L3·e2e)에서는 span이 버려진다.** 재채점(`--from-run`)만 읽을 수 있다.
  - OTel SDK 사용 0곳, Jaeger 없음. (`opentelemetry-sdk`·`otlp-proto-grpc` 1.45.1은 chromadb-client 의존성으로 이미 설치됨)
  - 실패 원인 분해: L3 리포트는 오류 유형(`wrong_value` 등)만, e2e는 `pass / retrieval / answer` 3칸. **"answer" 실패가 어느 단계 탓인지 0% 분해**.
    T1-27 재채점 기준 non-PASS 4건(86/90 PASS, `evals/reports/20261029-173056-T1-27-regrade`) — 단계 표시 0/4.

## Idea
1. **span 단위·속성 설계** (문항 1개 = trace 1개):
   ```
   eval.question  (root; qid, kind, layer, verdict, failure.stage, failure.reason)
   ├─ retrieve            (e2e·L1; retriever, k, top_keys, gold_rank, right_table)   ← 검색 단계
   └─ tool.summarize_stat (table_key, numbers_origin, outcome)                      ← 어떤 도구를 불렀는가
      ├─ judge            (outcome, rule, final)                                    ← 질문 이해(판정)
      ├─ analyze.rules / analyze.llm_fill[_retry]                                    ← 질문 이해(슬롯·계획)
      ├─ compute          (facts | outcome=refused, reason)                          ← 숫자 계산 모듈
      ├─ compose ×n / verify ×n / template                                          ← 문장 생성·검증·대체
      └─ fallback_chatbot (gen_ai.*)                                                 ← 계산 모듈 우회(LLM이 숫자 작성)
   ```
   LLM span 속성은 T1-22가 쓴 OTel GenAI 이름(`gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`) 그대로.
   토큰·비용은 Jaeger UI가 아니라 기존 `evals.ops`(ops.json·ops_history)에서 집계한다 — span 속성은 원천 기록일 뿐.
2. **span 수집**: evals runner가 `summarize_stat` 대신 같은 3줄(`api.table_path` → `api._build` → `bot.ask` → `to_stat_answer`)을 불러 `Answer.decision_metadata["spans"]`를 행에 보존한다.
   지금 runner도 client를 넘겨 `summarize_stat`이 문항마다 `_build`하므로 지연은 기준선과 같다. vendor/phase1은 수정하지 않는다. 재채점은 run 파일의 spans를 그대로 읽는다.
   한계: 실전 1의 private 함수(`_build`)에 의존한다 → `ponytail:` 주석으로 표시하고, 후속으로 실전 1에 `summarize_stat`이 spans도 돌려주게 하는 PR을 낸다(이 태스크 범위 밖).
3. **실패 단계 판정(결정적 코드)** `evals/trace.py: blame(row) -> {stage, span, reason}` — non-PASS 행만, **위에서부터 첫 번째로 맞는 규칙** 하나
   (grader `errors`는 집합이라 여러 개일 수 있어 순서로 정한다. 같이 나온 나머지 오류는 reason에 함께 적는다):
   | 순서 | stage | 조건 | span | 의미 |
   |---|---|---|---|---|
   | 1 | `retrieval` | e2e에서 1위가 정답 표 아님 / 검색 결과 없음 | `retrieve` | 검색 실패 |
   | 2 | `tool_call` | 답 없음(`run_failure`: 예외·모델 호출 실패)일 때만 | error span 중 마지막, 없으면 `tool.summarize_stat` | 도구 호출 자체 실패 |
   | 3 | `tool_skipped` | `fallback_chatbot` span 존재 (compute 미실행, numbers_origin=model) | `fallback_chatbot` (+reason에 앞서 실패한 `analyze.*`) | 숫자 계산 모듈을 건너뜀 |
   | 4 | `compute` | `compute` span이 refused/error인데 답 있는 문항 | `compute` | 계산 모듈이 거절·실패 |
   | 5 | `understanding` | 판정 오류(`false_refusal`·`missed_refusal`·`assumed_condition`·`wrong_reason`·`disallowed_default`·`unstated_default`·`missing_clarification`) → `judge` / 사실 오류(`wrong_value`·`wrong_unit`·`wrong_period`·`wrong_dims`·`missing_aux`) → 계획을 만든 마지막 `analyze.*` | `judge` / `analyze.*` | 질문 이해(판정·슬롯·계획) 실패 |
   | 6 | `compose` | `unsupported_claim`만 남음 | 마지막 `compose` | 문장 생성이 근거 없는 숫자 작성 |
   | 7 | `unknown` | 위에 안 맞음 | — | 규칙 보강 대상 (0이 목표) |

   - `tool_skipped`(3)를 `understanding`(5)보다 앞에 두는 이유: 사용자가 보고 싶은 것은 "계산 모듈을 건너뛰었다"는 에이전트 행동이다.
     근본 원인(앞서 실패한 analyze span)은 reason에 함께 적어 가려지지 않게 한다.
   - verify error(재시도 전 정상 흐름)·analyze.rules error(llm_fill로 넘어가는 정상 경로)는 답이 있으면 `tool_call`로 잡지 않는다.
   - 사실 오류를 `compute`가 아닌 `understanding`에 두는 근거: compute는 계획이 고른 셀을 결정적으로 계산할 뿐이라, T1-27 non-PASS 4건
     (`wrong_unit` 1 = 다른 항목 선택, `wrong_dims` 1, `missing_aux` 2 = 보조 셀 누락)은 모두 계획이 고른 셀 문제다.
4. **Jaeger 내보내기**: `OTEL_EXPORTER_OTLP_ENDPOINT`가 있으면 run 끝에 span dict를 OTel span으로 재생(시작·끝 시각 지정)해 OTLP gRPC로 보낸다. 없으면 아무것도 안 보낸다(오프라인 테스트·CI 영향 0).
   `docker-compose.yml`에 `jaeger` 서비스(`jaegertracing/all-in-one`, profile `obs`, UI 16686·OTLP 4317) 추가. 행마다 `trace_id` 저장.
5. **리포트**: `report.md`에 "실패 단계" 표(stage별 건수 + 문항별 stage·span·사유), `report.html`에 실패 단계 막대 + 문항별 **단계 타임라인**(span 순서, error span 빨강, 호출한 도구, Jaeger 링크).

## Option A — span dict로 실패 단계 판정만 (Jaeger 없음)
- 접근: Idea 2·3·5만. 기존 span dict를 그대로 읽어 판정·리포트에 표시. OTel SDK·Jaeger 미사용.
- 예상 성능 향상: non-PASS 단계 표시 0/4 → 4/4(T1-27 재채점, `unknown` 0 목표). n=4라 규칙 검증은 규칙별 pytest(합성 행)로 보완. e2e는 기준선 answer 실패 건수가 기록돼 있지 않아 수치 예상 없음(실행 시 측정). 답 품질 지표 변화 없음(관측만 추가).
- 실질 반영 이점: 결과 검증·예외 처리 근거(T2-13 실패 분석 표를 바로 만든다). 하지만 TASK.md의 "OpenTelemetry + Jaeger로 확정"을 충족 못 함.
- 비용·리스크: 2~3시간. 의존성 0. 리스크 낮음.

## Option B — A + OTel span 재생 → Jaeger (균형안)
- 접근: Idea 1~5 전부. 실행 중엔 지금처럼 dict를 모으고, run 끝에 OTel SDK로 trace를 재생해 Jaeger에 보낸다. 리포트에 trace_id·Jaeger 링크.
- 예상 성능 향상: A와 같음 + Jaeger에 문항당 trace 1개(90문항 → 90 trace) 확인 가능. 재채점(과거 run)도 Jaeger에 올릴 수 있다.
- 실질 반영 이점: TASK.md 도구 결정 충족, 발표에서 Jaeger 화면으로 "어느 span에서 실패" 시연. 종합(LangGraph 에이전트)에서 같은 `eval.question → tool.* → 단계` 구조를 그대로 쓴다.
- 비용·리스크: 반나절. 새 패키지 설치 0(이미 있음, pyproject에 직접 의존성으로만 명시). Jaeger는 선택 실행이라 꺼져 있어도 평가가 돈다. 재생 방식이라 실시간 스트리밍은 아님.

## Option C — 실시간 계측 (LangChain 콜백 → OTel + FastAPI 자동 계측)
- 접근: B + `src/kosis_rag` 체인·검색기에 OTel 콜백 핸들러, backend에 `opentelemetry-instrumentation-fastapi`, 실서비스 요청마다 trace. Phase 1 단계는 여전히 dict 재생.
- 예상 성능 향상: 평가 지표는 B와 같음. 운영 요청 단위 관측(데모·배포)이 추가.
- 실질 반영 이점: 종합 단계 운영 관측 미리 확보.
- 비용·리스크: 하루+. 계측 패키지 추가, LangChain 콜백·컨텍스트 전파 디버깅. 아직 서비스 API(T2-10)가 없어 계측할 요청이 거의 없다 → 지금은 과함.

## Recommendation
**Option B.** 사용자가 요청한 "어느 trace·span에서 왜 실패"를 리포트와 Jaeger 양쪽에서 보여주고, 의존성 추가 없이 반나절에 끝난다.
C는 T2-10(검색 API) 이후 서비스 요청이 생기면 그때 붙인다.
