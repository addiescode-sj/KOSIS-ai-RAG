# T2-37 노드 단위 FastAPI (StreamingResponse · BackgroundTasks · SSE + Swagger)

## Goal
- 완료 기준 (TASK.md 그대로): LangGraph 검색 노드(parse·retrieve·rerank1·rerank2·gate·answer)를 기능별 endpoint로 노출하고,
  StreamingResponse·BackgroundTasks·SSE로 비동기 처리, Swagger(OpenAPI) 문서. 완료 기준: 노드별 endpoint, SSE 노드 이벤트 스트림,
  노드 체인 결과 = `run_search` 결과(pytest), `docs/openapi.json`
- Baseline: 백엔드는 `/health` 하나 (`backend/app/main.py` 8줄). 검색·챗 endpoint 0개, OpenAPI 경로 1개.
  검색 지표(Hit@k·MRR)는 바꾸지 않는다 — API는 같은 그래프 노드를 부르는 껍데기다.

## Idea
1. **노드 함수 꺼내기 (동작 변경 없음)** — `graph.build_graph` 안의 클로저(parse·retrieve·rerank1·rerank2·gate·refuse·guide)를
   `graph.make_nodes(resources, client, k) -> dict[str, Callable[[SearchState], dict]]`로 꺼내고, `build_graph`는 그 dict로 그래프를 짓는다.
   그래프와 API가 같은 함수를 부른다. 기존 `tests/test_graph.py`가 회귀를 막는다.
2. **자원 로딩** — `load_resources()` + 안내 LLM(`chain.clova_chat()`)은 무겁다. 첫 요청 때 한 번 만들고(lock) `Depends(get_runtime)`으로 주입한다.
   lifespan에서 만들지 않는 이유: Chroma·`data/` 마운트가 없으면 앱이 아예 안 떠 `/health`까지 죽는다 (리뷰 5). 로딩 실패는 503.
   테스트는 `app.dependency_overrides`로 test_graph의 가짜 자원을 넣는다 (Chroma·LLM 없이).
3. **SSE·StreamingResponse** — FastAPI 0.162 내장 `fastapi.sse.EventSourceResponse`(StreamingResponse 하위 클래스, 새 의존성 0).
   동기 `graph.stream(stream_mode=["updates", "values"])`를 sync generator로 넘긴다(Starlette가 스레드풀에서 순회, 루프 안 막음).
   노드가 끝날 때마다 `event: <node>` + **그 노드의 trace 항목만**(trace는 누적이라 통째로 보내면 중복, 리뷰 3b),
   마지막에 `values`의 최종 상태로 `event: result` = `SearchResult`.
4. **BackgroundTasks** — 응답을 보낸 뒤 `logs/api/<date>.jsonl`에 한 줄 append: 질문·노드별 seconds·route·상위 5 key·answer_origin.
   평가 리포트(노드별 지연)의 재료. `logs/`는 gitignore, Docker에선 컨테이너 안(휘발) — 보존이 필요해지면 볼륨을 단다.
5. **Swagger** — FastAPI 자동 `/docs`(Swagger UI)·`/redoc`에 tag(nodes / search / ops), summary, description, 요청 예시.
   `scripts/export_openapi.py`로 `docs/openapi.json`을 떨군다 (서버 없이 `app.openapi()`).
6. **배포 보완** — `backend/Dockerfile`이 `src/`를 복사하지 않고 PYTHONPATH에 `/app/src`가 없다 → 두 줄 추가.
   compose에 `data/`는 이미 읽기 전용 마운트, Chroma는 서비스 이름으로 연결. 리랭커 체크포인트(`RERANK_CKPT`)는 `.env` 경로가
   `data/` 아래면 그대로 보이고, 아니면 1차 리랭커 없이 뜬다 (그래프가 rerank1을 빼고 짓는다) — Result에 확인 결과를 적는다.

공통 원칙: 표 ID·출처는 서버의 레코드(`resources.records`)에서만 나온다. 숫자는 만들지 않는다(검색·안내만). 거절 경로는 그래프의 gate → refuse 그대로.

## Option A — 클라이언트가 잇는 무상태 노드 API + 전체 그래프 SSE
- 접근: 노드마다 endpoint, 상태를 받아 상태를 돌려준다. 클라이언트가 parse → retrieve → … 를 직접 잇거나, 중간 상태를 고쳐 한 노드만 다시 부른다.
  | 경로 | 노드 | 입출력 |
  |---|---|---|
  | `GET /nodes` | — | 켜진 노드 순서 (rerank1·2는 설정에 따라) |
  | `POST /nodes/parse` | parse | `{question}` → `SearchState` |
  | `POST /nodes/retrieve` · `/rerank1` · `/rerank2` · `/gate` | 각 노드 | `SearchState` → `SearchState`. 꺼진 리랭커는 409 |
  | `POST /nodes/answer` | refuse \| guide | `SearchState`(route 필요, 없으면 422) → `SearchState`(result) |
  | `POST /search` | 전체 | `SearchArgs` → `SearchResult` (+ BackgroundTasks 로그) |
  | `POST /search/stream` | 전체 | SSE 노드 이벤트 → `event: result` (+ BackgroundTasks 로그) |
  - **입력 docs 재접지 (리뷰 2)**: 클라이언트가 보낸 `docs`의 각 key가 `resources.records`에 없으면 422. 있으면 `page_content`와
    카탈로그 필드(표명·조사명·기관·수록기간·url)를 레코드로 덮어쓴다. 검색 메타데이터(score·rank·stage*)만 클라이언트 값을 쓴다.
    → 순서·점수는 바꿔 볼 수 있어도 없는 표나 가짜 출처는 만들 수 없다.
- 예상 성능 향상: 검색 지표 변화 없음 (같은 노드, 결과 동일 pytest로 고정). 사용자가 보는 첫 이벤트까지 시간: 전체 응답
  (기본 1차만 p50 0.57초 `plans/T2-07.md`, HCX 2차 p50 10.9초 `plans/T2-09.md`) → parse 이벤트(규칙만, ms 단위).
  결과가 나오는 시간 자체는 같다 (리뷰 1) — 진행 표시가 생길 뿐.
- 실질 반영 이점: 기능 완성도·기술 설계. 노드 하나만 바꿔 넣는 디버깅·시연(Swagger). T2-11 UI 진행 표시, 종합 단계 툴 호출에 재사용.
- 비용·리스크: 반나절. 재접지 코드와 입력 검증이 늘어난다. LLM 비용 추가 없음.

## Option B — 서버가 상태를 쥔 실행(run) + 노드별 조회 endpoint
- 접근: `POST /runs`가 run id를 즉시 돌려주고 BackgroundTasks로 그래프를 돌린다. 노드가 끝날 때마다 서버 메모리에 그 노드의 출력을 저장.
  `GET /runs/{id}` (상태·결과) · `GET /runs/{id}/nodes/{node}` (그 노드 출력, 노드 단위 endpoint) · `GET /runs/{id}/events` (SSE, 지난 이벤트부터 재생).
  클라이언트는 상태를 보내지 않는다 → 재접지가 필요 없다.
- 예상 성능 향상: A와 같다. 추가로 연결이 끊겨도 같은 run을 다시 받는다 (HCX 2차 ~11초 요청에서 의미).
- 실질 반영 이점: 예외 처리(끊김·재시도). 평가 배치를 API로 돌릴 수 있다. 노드를 "고쳐 넣는" 디버깅은 못 한다.
- 비용·리스크: 1일. 메모리 저장이라 워커 2개 이상·재시작 시 run 유실 → 단일 워커 전제, TTL 정리 필요.
  기본 설정 요청이 짧아(p50 0.57초) 지금 실익이 작다.

## Option C — 채팅 endpoint 하나 + 안내 LLM 토큰 스트리밍
- 접근: 노드별 HTTP endpoint 없이 `POST /chat` SSE 하나. 노드는 이벤트 종류(`event: parse` …)로만 드러나고, guide에서
  `llm_runnable(client).astream()`으로 `event: token`을 흘린 뒤 검증(`unsupported_claims` → 실패 시 템플릿)·출처 부착 후 `event: result`.
- 예상 성능 향상: 안내 문장 첫 토큰까지 시간 = LLM 전체 생성 → 첫 토큰(추정 1초 미만, 근거: 스트리밍 일반 특성, 이 프로젝트 측정 없음).
- 실질 반영 이점: 응답 품질 체감. 단 **검증 전 문장이 먼저 화면에 나간다** — 템플릿으로 바뀌면 사용자가 지워질 문장(지어낸 표·연도일 수 있음)을 본다.
  데이터 정확성 원칙과 충돌. 요청한 "노드 기능 단위 endpoint"도 빠진다.
- 비용·리스크: 1일. `chain.guide_answer`를 스트리밍용으로 쪼개야 해 그래프와 API 경로가 갈라진다(결과 동일 pytest 어려움).
  Phase 1 `MockClient`에 스트리밍이 없다 (`vendor/phase1/kosis_chat/llm/model.py`) → 테스트용 가짜를 새로 만들어야 한다.

## Recommendation
**Option A.** 요청한 노드 기능 단위 endpoint와 StreamingResponse(SSE)·BackgroundTasks·Swagger를 모두 담고, 새 의존성 없이
그래프와 같은 함수를 불러 결과 동일을 pytest로 고정할 수 있다. 재접지로 출처 원칙도 지킨다. B는 요청이 짧은 지금 실익이 작고
노드 디버깅을 못 하며, C는 검증 전 문장 노출이 데이터 정확성 원칙과 부딪친다. B의 run 저장은 A 위에 나중에 얹을 수 있다.

## Measure
지표는 검색 수치가 아니라 다음 세 가지 (리뷰 1):
1. 결과 동일 (pytest, 가짜 자원): 노드 endpoint를 이어 부른 결과 = `/search` = `/search/stream`의 `event: result` = `run_search`.
   검색 결과·`SearchResult` 필드 일치 문항 수 / 전체.
2. 재접지: 없는 key 422, 가짜 표명·url은 레코드 값으로 덮임 (pytest).
3. 지연 (로컬 실서버, Chroma 있을 때): 질문 N개로 첫 SSE 이벤트까지 시간 vs `/search` 전체 응답 시간, 노드별 seconds(로그) p50.
   실서버가 없으면 그렇게 적는다.
