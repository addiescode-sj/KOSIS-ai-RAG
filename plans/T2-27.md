# T2-27 표 역할 분리 — 세는 대상과 나누는 기준 (T2-25 서브 이슈, Linear KOS-92)

## Goal
- 완료 기준 (TASK.md 그대로): "출생"이 들어간 표 146개, "혼인"이 들어간 표 241개처럼 같은 단어가 세는 대상과 분류 기준으로 섞여 검색이 희석된다. 정보를 지우지 않고 표마다 세는 대상(measure)과 나누는 기준(dimensions)을 나눠 검색에 반영한다. 검색 성능 측정은 평가 엔지니어링이 맡는다
- **평가 범위 (2026-11-02, 임도유 지시)**: 평가는 AI 평가 엔지니어링(이선주) 담당이다. 이 태스크는 데이터 처리와 검색 반영까지만 하고, 골든셋 전후 측정·평가 하네스 변경은 하지 않는다. 평가 쪽이 바로 잴 수 있게 빌드 이름과 사용법을 넘긴다.
- 기준 브랜치: PR #17(T2-14 필터, 평가 코드 뺀 버전) + PR #10(T2-25 1+2+3 문서 형식)을 합친 위. 둘 다 미머지라, 머지되면 master로 다시 맞춘다.
- 배경 (데이터 확인, 2026-11-02):
  - 표 이름 "A/B/C별 X" 형태가 2,364개 중 2,090개. "혼인"이 든 표 241개 중 182개, "출생"이 든 표 146개 중 102개는 그 단어가 **나누는 기준(A/B/C)**에만 있다(혼인상태별 인구, 출생지별 인구, 출생아수별 부인).
  - 짧은 질문 몇 개로 확인해 보면 "출생아 수"는 상위 10개 중 3개가 `…출생아수별 부인` 같은 분류 역할 표였고, "혼인 건수"는 0개였다. 반대로 "태어난 곳별 인구", "미혼 인구"처럼 **분류 역할 표가 정답인** 질문도 있다. → 분류 역할 표를 무조건 뒤로 보내면 안 되고, 역할을 밝히는 쪽이어야 한다.

## Idea
1. **역할 함수** `table_roles(record) -> (measure, dimensions)` (`src/kosis_rag/roles.py`): `TableRecord`에 필드를 넣지 않고 레코드에서 바로 계산하는 순수 함수로 둔다(스키마·`tables.jsonl` 호환 문제 없음, 리뷰 반영).
   - 표 이름 "A/B/C별 X"(2,090표): dimensions = A/B/C, measure = X.
   - 이름 규칙의 함정을 테스트로 고정한다: "특별시"·"성별"처럼 단어 안의 "별", "성 및 연령별"·"시도·시군구별" 같은 구분자 혼용, 괄호 꼬리("(1세 이상)", "-시군구"), X 안의 수식어("북한출생 인구" → measure 인구).
   - 이름이 형태에 맞지 않는 274표: dimensions는 분류 이름(`classes[].name`)으로 채우고, **measure는 빈 값**으로 둔다(항목이 계·남자·여자 같은 분류값인 표가 많아 잘못된 값이 들어가기 쉬움, 리뷰 반영).
2. **검색 반영**은 옵션마다 다르다(아래).
3. **데이터 품질 확인 (평가 아님)**: 단위 테스트 + 층화 표본 50표(이름 형태 맞음 / "별"이 단어 안에 있음 / 괄호 꼬리 / 형태 안 맞음 274표에서 고르게)를 사람이 보고 measure·dimensions가 맞는지 확인한다. T2-09가 `dimensions`로 "분류 불일치" 거절을 하려면 이 정확도가 높아야 한다(잘못 뽑으면 잘못된 거절이 된다) → 표본 정확도를 결과에 적고, 95% 미만이면 T2-09에 넘기지 않는다.

## Option A — 역할 함수만 (검색은 그대로)
- 접근: 1번 함수와 테스트만 만든다. 임베딩 문서와 순위는 바꾸지 않는다.
- 예상 효과: 검색 결과 변화 없음. 표마다 세는 대상·나누는 기준을 코드로 얻을 수 있게 된다(0 → 2,364표, measure는 약 2,090표).
- 실질 반영 이점: 멘토 Q5의 `dimensions`가 생긴다. T2-09 "분류 불일치" 거절과 T2-11 안내 문구("이 표는 시도·성·연령별 혼인 건수입니다")에 바로 쓰인다.
- 비용·리스크: 반나절. 사용자가 제기한 "희석" 자체는 해결하지 않는다.

## Option B — A + 임베딩 문서에 "세는 대상" 표시 (문서 쪽)
- 접근: A + 1+2+3 문서의 맨 앞 요약 줄에 `세는 대상: {measure}`를 넣는다. 나누는 기준은 다시 쓰지 않는다 — `…출생아수별 부인`에 "출생아수"를 한 번 더 쓰면 오히려 그 단어가 강해진다(리뷰 반영). `DOC_FORMAT`을 새 이름으로 올리고 **새 빌드 컬렉션을 하나 더 만든다**(약 7분). 서비스 기본 컬렉션(`CHROMA_COLLECTION`)은 바꾸지 않고, 평가 엔지니어링이 1+2+3 빌드와 비교한 뒤 전환을 정한다.
- 예상 효과: "출생아 수"처럼 단어가 두 역할로 쓰이는 질문에서 세는 대상이 맞는 표가 앞에 올 것을 기대한다. 다만 표지어("세는 대상:")는 모든 문서에 똑같이 붙어서, 임베딩이 이를 얼마나 반영할지는 불확실하다(리뷰 지적). 효과 판단은 평가 쪽 측정으로 한다.
- 실질 반영 이점: 데이터 전처리 범위 안에서 정보를 지우지 않고 역할만 밝힌다(T2-25 연장). 질문 해석 규칙이 없어 질문 표현에 맞춰질 위험이 없다. 옛 빌드를 남겨 되돌리기 쉽다.
- 비용·리스크: 반나절~1일(함수 + 문서 형식 + 새 빌드 적재). 효과가 없으면 빌드 하나가 남는 것뿐이다.

## Option C — A + 질문 의도 판정 후 순위 조정 (검색 후 쪽)
- 접근: A + 질문이 단어를 **세는 대상**으로 쓰는지("혼인 건수", "출생아 수") **나누는 기준**으로 쓰는지("미혼", "혼인상태별", "태어난 곳")를 규칙으로 판정해, 검색 후 역할이 맞는 표를 앞으로 보낸다(soft, 빼지 않음). 재적재 없음. T2-14 `ConditionRetriever`에 붙인다.
- 예상 효과: 판정이 맞으면 B보다 직접적이다. 판정 규칙이 틀리면 정답을 뒤로 보낼 수 있다.
- 실질 반영 이점: 양방향(세는 대상 / 나누는 기준)을 명시적으로 다룬다.
- 비용·리스크: 1일. 질문 표현 규칙을 몇 개 예시에 맞춰 만들 위험이 크고, 리랭커(T2-07, 전민기)와 역할이 겹친다. 데이터 엔지니어링보다 검색 엔지니어링 범위에 가깝다.

**표 묶음(family)으로 결과 다양화**는 넣지 않는다. 검색 결합 단계(T2-06·T2-07, 전민기)에서 하는 게 자연스러워 방법만 공유한다.

## Recommendation
**Option B.** 사용자가 제기한 원인(같은 단어의 두 역할)을 데이터 전처리 쪽에서 직접 다루고, 정보를 지우지 않는다. 새 빌드를 따로 만들고 기본 컬렉션은 그대로 두므로, 효과 판단을 평가 엔지니어링에 맡기는 이번 범위와 맞는다. A는 함수만 만들어 희석 문제를 그대로 두고, C는 질문 규칙 과적합 위험이 있고 검색 엔지니어링 범위와 겹친다.
