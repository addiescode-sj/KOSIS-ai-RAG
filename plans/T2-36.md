# T2-36 LangGraph 노드 단위 tracing (KOS-87 선행)

## Goal
- 완료 기준 (TASK.md 그대로): T2-10에서 검색이 LangGraph 노드(parse·retrieve·rerank1·rerank2·gate·refuse|guide)로 바뀌었는데
  `evals/trace.py`는 검색을 `retrieve` span 하나로만 본다. 노드마다 span을 남기고, 검색 실패를 정답 표가 빠진 노드로 판정하고,
  Jaeger·report에 노드 타임라인을 낸다. 완료 기준: `graph:<preset>` 실행에서 노드 span 수집, 검색 실패의 노드 판정 비율, pytest
- KOS-87(실전 3, 11/14)과의 관계: KOS-87 첫 항목 "노드마다 OpenTelemetry span, 내부 API 호출(LLM) 하위 span"과 "LLM 토큰은 span 속성"을
  실전 2 검색 그래프에서 먼저 한다. Ragas 비동기 평가·T3 하네스 연결·실전 3 노드(Fetch→Compute→…→Chart)는 이 태스크 범위 밖.
- Baseline (코드 기준, 11/03 master `ae9cf50`):
  - `graph:<preset>`으로 돌린 L1·e2e에서 **노드 span 0개**. 그래프 상태의 `trace`(노드별 seconds·n_docs·route·stage2_*)는
    `retrieval.build`의 `RunnableLambda`가 `.docs`만 돌려줘 버려진다.
  - e2e trace는 `eval.question → retrieve(1개) → tool.summarize_stat → Phase 1 span`. 검색 실패는 모두 `retrieve` 한 곳 탓
    → **검색 실패의 노드 판정 0%** (후보 풀에 아예 없었는지, rerank1·rerank2가 밀어냈는지 구분 불가).
  - L1은 trace를 아예 안 만든다 (`trace.export`는 l3·e2e만).

## Idea
1. **노드 span 수집** — LangGraph는 노드마다 LangChain 콜백을 낸다 (scratch 확인: `on_chain_start` name=노드명,
   metadata `langgraph_node`=노드명, tag `graph:step:N`; `on_chain_end` outputs=노드가 돌려준 dict(`docs`·`route`·`trace`…);
   guide 노드 안의 `phase1_llm:*` 호출도 같은 `langgraph_node`로 온다). 이걸 Phase 1과 **같은 span dict 모양**
   (`name·start_ms·duration_ms·status·attributes`)으로 모은다 → 기존 `blame`·`export`·`report_html.timeline`을 그대로 재사용.
2. **노드 속성**: `top_keys`(상위 5), `n_docs`, `n_removed`(retrieve), `route`·`refusal_reason`(gate), `origin`(guide),
   `stage2_*`·토큰(rerank2: CLOVA/HCX를 직접 불러 콜백이 없으므로 문서 메타데이터에서). 노드 안 LLM 하위 span은 실제 LangChain 모델이
   붙는 서비스 경로(실전 3)에서 의미가 있어 이번엔 뺀다.
3. **검색 실패의 노드 판정**(결정적 코드): 노드마다 정답 키들 중 **가장 좋은 순위**(풀 전체 기준, 없으면 ∞; 순위는 리스트 위치라 동점 없음)를 구한다.
   기준 k(L1 = Hit@k의 k, e2e = 1)에 대해 `≤k → >k`로 **마지막으로 떨어뜨린 노드**가 범인. 한 번도 ≤k가 아니었으면 `retrieve`
   (사유: 풀에 없음 / 풀 n위). retrieve에서 >k였다가 rerank가 올렸는데 뒤 노드가 다시 내리면 그 뒤 노드.
   L1 답 없음 오판(답 있는데 거절 / 답 없는데 안내)은 `gate`(decide_route). e2e는 기존 `right_table=False` 규칙 1의 span 이름만 노드로 바꾼다.
4. **Jaeger 트리**: `eval.question → search_tables(그래프) → parse / retrieve / rerank1 / rerank2 / gate / guide(→ llm)`,
   e2e는 그 옆에 기존 `tool.summarize_stat`. 그래프가 아닌 검색기는 지금처럼 `retrieve` 하나.
5. **리포트**: report.md 실패 단계 표와 report.html 타임라인에 노드가 그대로 나온다(기존 코드가 span 리스트를 그림).

## Option A — 그래프 상태를 e2e에서만 재생
- 접근: `graph.py` 노드의 `timed(...)`에 `top_keys`를 더하고, e2e runner가 `graph:<preset>`이면 `run_search`를 직접 불러
  `state.trace`를 span dict로 바꿔 `retrieve` 아래 자식으로 재생. L1은 손대지 않는다.
- 예상 성능 향상: e2e 검색 실패의 노드 판정 0% → 100%(그래프 preset 한정). 노드 span 0 → 질문당 5~6개(e2e만). L1 0 → 0.
  검색·답 지표 자체 변화 없음(관측만 추가).
- 실질 반영 이점: 결과 검증. 하지만 그래프 출력 계약(`state.trace`)에 평가용 필드를 넣고 e2e runner에 그래프 분기가 생긴다.
  LLM 하위 span·토큰 없음. KOS-87에 그대로 못 가져간다(state 형식에 묶임).
- 비용·리스크: 2~3시간. `src/kosis_rag/graph.py` 수정 → 전민기 담당 코드와 충돌 가능.

## Option B — LangChain 콜백으로 노드 span 수집, 재생 방식 유지 (L1·e2e 공통)
- 접근: `evals/trace.py`에 `NodeSpans(BaseCallbackHandler)` 하나, 문항마다 새로 만든다(`UsageCallback`과 같게).
  **노드 run만** 기록: `name == metadata["langgraph_node"]`이고 부모가 그래프 root run인 것(태그·metadata가 ChannelWrite·gate 분기 lambda·
  내부 runnable에도 내려가므로 태그만으로 거르면 중복). `on_chain_end`에서는 `docs` 전체가 아니라 `ranked_keys`(풀 전체 키 순서)만 보관.
  L1 runner는 기존 `config` callbacks에 추가, **e2e runner는 지금 `invoke`에 config가 없어 넘기도록 수정**.
  노드 span은 Phase 1 span(`row["spans"]`)과 **섞지 않고 `row["search_spans"]`** 별도 필드 → 기존 `blame`·`export`·`timeline` 규칙 불변.
  L1용 판정은 별도 함수 `blame_search(row, gold, k)`(L1 행에 verdict가 없음), e2e는 규칙 1의 span만 노드로 바꾼다.
  `export`는 L1에도 열되 지금처럼 `OTEL_EXPORTER_OTLP_ENDPOINT`가 있을 때만(opt-in, 새 플래그 없음). `src/kosis_rag`·vendor 수정 0.
- 예상 성능 향상: 노드 span 0 → 질문당 5~6개(parse·retrieve·[rerank1]·[rerank2]·gate·refuse|guide). **LLM 하위 span은 0**:
  평가의 guide는 Phase 1 `MockClient`(LangChain 모델 아님), rerank2는 CLOVA/HCX 직접 호출 → rerank2 노드 속성에 `stage2_calls`·토큰만.
  검색 실패 분포 미분해 → **노드별 실패 건수**(retrieve n / rerank1 n / rerank2 n / gate n, 합 = 검색 실패 수)로 보고.
  L1 Jaeger trace 0 → 문항당 1개(endpoint 설정 시). 그래프 아닌 검색기는 지금과 같은 결과(회귀 0, pytest로 고정).
- 실질 반영 이점: 결과 검증·기술 설계. T2-13 실패 분석에 "어느 노드가 정답 표를 밀어냈나" 표를 바로 쓴다(리랭커 효과를 문항 단위로 증명).
  콜백은 그래프 구조를 몰라도 되므로 실전 3 LangGraph(Fetch→…→Chart)에 **그대로 붙는다** → KOS-87 1·2항의 토대.
- 비용·리스크: 반나절. 의존성 추가 0(langchain_core·opentelemetry 이미 설치). 리스크: LangGraph 콜백 태그 형식 의존
  → pytest로 고정, 바뀌면 노드 span이 0개로 보여 바로 드러난다. 재생 방식이라 실시간 아님(T2-15와 같음).

## Option C — 실행 중 OTel span (서비스·평가 공용 계측기)
- 접근: B의 콜백이 dict 대신 **실제 OTel span을 실행 중에 연다** (`src/kosis_rag/tracing.py`, service `kosis-rag`).
  backend 검색 API 요청도 trace, LLM 토큰은 OTel 메트릭(`gen_ai.client.token.usage` Counter). 평가 root span도 실시간으로 열고,
  verdict·failure는 채점 후 속성으로 못 붙이므로 별도 링크 span으로 단다. Phase 1 span은 여전히 dict 재생.
- 예상 성능 향상: 평가 지표는 B와 같음. 운영 요청 단위 관측 + 토큰 메트릭 추가(KOS-87 1·2항 거의 완료).
- 실질 반영 이점: KOS-87을 앞당겨 거의 끝냄. 데모에서 실제 요청 trace.
- 비용·리스크: 하루+. 실시간 span과 사후 채점 결과를 잇는 설계(링크 span·meter provider)가 새로 필요하고, 실전 1 Phase 1 span과
  시계가 섞인다. backend 검색 API가 아직 확정 전(T2-10 [ ])이라 계측할 요청이 적다. 실전 3 노드가 생긴 뒤 하는 편이 재작업이 적다.
