# T2-11 안내 챗봇 데모 (+ T2-17 중 로컬 Docker Compose 기동)

## Goal
- 완료 기준 (TASK.md 그대로): 안내 챗봇 데모 (산출물③) — 추천에 기관·수록기간·링크, 답 없으면 없다고 말함
- 이번 범위 (사용자 지시 11/03): 도메인 연결·EC2 배포는 하지 않는다. `docker compose up --build`로 **각자의 컴퓨터에서** chroma·backend·frontend가
  같이 뜨게 한다 (T2-17의 로컬 부분만, 서버 배포·스모크는 T2-17에 남김).
  프론트는 확정 스택 Next.js 16 App Router + Tailwind 4 + shadcn/ui로 간단한 RAG 챗봇. T2-37 SSE(`/search/stream`)의 노드 이벤트가
  화면에 단계별로 보이고, 사용자 질의가 endpoint를 거쳐 파이프라인 끝(`event: result`)까지 가는 것을 확인할 수 있는 정도.
- 담당: TASK.md 표에는 임도유. 사용자 지시로 이번 작업을 진행한다 (팀 공유 필요).
- Baseline: 프론트는 create-next-app 기본 페이지 (채팅 UI 0). compose `backend`는 이미지 빌드는 되지만 **검색 불가**:
  질의 임베딩에 필요한 `sentence-transformers`가 `embed` 의존성 그룹에만 있어 이미지(`uv sync --no-dev`)에 없다.
  T2-37 전에는 `src/`도 이미지에 없었다(T2-37에서 수정).

## Idea
1. **백엔드 컨테이너가 실제로 검색하게**
   - `backend/Dockerfile`: `uv sync --frozen --no-dev --group embed` (sentence-transformers·torch). 장치는 설정하지 않는다
     (`SearchSettings.from_env`가 장치를 읽지 않음 → CPU, 맥 MPS는 컨테이너 안에서 안 보임).
   - KURE-v1 가중치: compose `hf-cache` named volume(`/root/.cache/huggingface`). 첫 검색 요청이 다운로드(수백 MB)를 기다리므로
     README 절차에 "처음 한 번 `/nodes` 호출로 예열"을 적는다 (Next 프록시 fetch는 기본 헤더 타임아웃 300초라 끊기지 않음).
   - **Chroma 컬렉션** (리뷰 2): compose `chroma`는 `chroma-data` named volume. 이미 색인한 컴퓨터(내 컴퓨터: `kosis_a_kure_202610301530` 2,364표)는
     그대로 쓰고, 빈 볼륨이면 `docker compose run --rm backend python -m kosis_rag.index`로 CPU 색인 (소요 시간을 Result에 기록) 후
     출력된 이름을 `.env` `CHROMA_COLLECTION`에. 공용 Chroma가 배포되면 compose의 `CHROMA_HOST`/`CHROMA_PORT`를
     `${COMPOSE_CHROMA_HOST:-chroma}` 식으로 열어 두어 `.env`만 바꿔 붙게 한다.
   - 조건 문서화: bge-ft 컬렉션이면 `EMBED_CKPT`, 1차 리랭커면 `RERANK_CKPT`가 `data/models/` 아래(읽기 전용 마운트로 보임), `STAGE2`·안내 LLM은 `HCX_API_KEY`
     (없으면 안내 문장은 코드 템플릿으로 대체 — 거절·출처는 그대로).
   - healthcheck (리뷰 4): slim 이미지에 curl 없음 → `python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health')"`.
     `/health`는 검색 자원을 안 읽으므로 healthy ≠ 검색 가능 — 프론트는 503을 오류 말풍선으로 보여 준다.
2. **프론트 → 백엔드 연결** — 브라우저는 Next 서버만 부른다. Route Handler `app/api/chat/route.ts`가 서버 전용 env `BACKEND_URL`
   (compose `http://backend:8000`, 로컬 dev 기본 `http://localhost:8000`)로 `POST /search/stream`을 프록시하고 SSE 본문을 그대로 흘린다
   (`backend-for-frontend.md` "Proxying to a backend"). CORS 불필요, 백엔드 주소가 브라우저에 안 나감.
   `BACKEND_URL`은 핸들러 안에서 요청마다 읽는다(모듈 상수·next.config rewrites는 빌드 때 고정, 리뷰 4). 응답에 `Content-Type: text/event-stream`,
   `Cache-Control: no-cache, no-transform`을 직접 달아 압축·버퍼링을 막고, `fetch(..., { signal: request.signal })`로 사용자의 중단을 백엔드까지 전한다.
3. **채팅 화면 (`app/page.tsx` + `components/chat/*`)**
   - 입력창 → 사용자 말풍선 → 진행 단계 줄(parse → retrieve → [rerank1] → [rerank2] → gate → guide|refuse, 노드 이벤트가 올 때마다 체크와 ms 표시)
     → `event: result`가 오면 답변 말풍선 + 후보 표 카드(표명·조사명·기관·수록기간·KOSIS 링크).
   - 답 없음(`no_answer`)은 다른 색 말풍선으로 "맞는 표가 없다" 문장. `event: error`·HTTP 오류·503은 오류 말풍선.
   - 숫자는 화면이 만들지 않는다. 답변 문장·출처는 백엔드 `SearchResult` 그대로 (출처 줄은 백엔드가 붙인 텍스트).
   - shadcn/ui: Button·Input·Card·Badge·ScrollArea만 (`npx shadcn@latest init` + `add`), 나머지는 Tailwind.
4. **SSE 파서** — `EventSource`는 GET만 되므로 `fetch` + `ReadableStream` reader로 `event:`/`data:` 블록을 직접 나눈다(`lib/sse.ts`, 20줄 안팎).
   비자명 로직이라 테스트 하나: Node 내장 `node:test`로 조각난 청크·여러 이벤트를 나누는지 확인 (새 테스트 프레임워크 없음).
5. **확인 방법** — compose로 띄운 뒤 Playwright(이미 있는 `playwright-cli` skill)로 질문 N개를 입력해, 노드 이벤트 수·`result` 도착·첫 단계 표시까지 시간을 잰다.

## Option A — Route Handler 프록시 + 직접 만든 SSE 파서 (최소안)
- 접근: 위 Idea 그대로. 상태는 React `useState` 하나(메시지 배열), 대화는 새로고침하면 사라짐.
- 예상 성능 향상: 채팅 UI 0 → 1. 백엔드 지표 변화 없음. 사용자가 보는 첫 반응: 전체 응답 대기(로컬 p50 118.5 ms, HCX 2차 켜면 ~10.9초, T2-09)
  → 첫 노드 표시(T2-37 SSE 첫 이벤트 p50 26.6 ms + 프록시 1홉, 추정 수십 ms). compose 백엔드 검색 가능 0 → 1.
- 실질 반영 이점: 산출물③ 데모, 기능 완성도(출처 카드·거절 표시), 예외 처리(오류 말풍선). 노드 진행 표시가 발표 시 파이프라인 설명이 된다.
  의존성은 shadcn이 까는 것(radix 일부·cva·clsx·tailwind-merge·lucide)뿐.
- 비용·리스크: 1일 (색인·이미지 빌드 대기 포함). 백엔드 이미지가 torch 때문에 커진다: `uv.lock`의 리눅스 torch 2.15는 `sys_platform == 'linux'`에서 nvidia-*-cu13·triton을 함께 설치 →
  CPU만 쓰는데도 수 GB(첫 빌드 수 분). CPU 전용 torch는 `[tool.uv.sources]`에 pytorch-cpu 인덱스(linux marker) + `uv lock` 재생성 →
  팀 전체 락이 바뀌므로 별도 결정으로 묻는다(아래 Decision). 안 바꾸면 이미지 크기를 Result에 적는다. 첫 질의는 KURE 다운로드로 느림(volume 이후엔 없음).

## Option B — Vercel AI SDK `useChat` + 백엔드 SSE → UI 메시지 스트림 변환
- 접근: `ai`·`@ai-sdk/react` 설치. Route Handler가 백엔드 SSE를 읽어 AI SDK UI message stream 프로토콜(노드 이벤트는 data part, 답변은 text part)로 바꿔 보낸다.
  화면은 `useChat`이 메시지·로딩·중단(stop)·재시도를 관리.
- 예상 성능 향상: A와 같음 (같은 백엔드 이벤트).
- 실질 반영 이점: 중단·재시도·메시지 상태를 직접 안 짠다. 종합 단계에서 LLM 토큰 스트리밍(T2-37 옵션 C)을 붙일 때 그대로 쓸 수 있다.
- 비용·리스크: +반나절. 의존성 2개와 변환 계층이 생기고, SDK 프로토콜 버전(v5/v6) 변화에 묶인다. 지금 백엔드는 토큰이 아니라
  완성된 `SearchResult` 한 번이라 SDK의 주 기능(토큰 스트림)을 거의 안 쓴다.

## Option C — 브라우저가 백엔드 직접 호출 (CORS) + Server Component 초기 화면
- 접근: 프록시 없이 브라우저가 `NEXT_PUBLIC_API_URL`(빌드 때 박힘)로 FastAPI를 직접 부른다. 백엔드에 `CORSMiddleware`(localhost:3000 허용).
  프론트 서버 코드 0, Next는 정적 화면만.
- 예상 성능 향상: A보다 프록시 1홉만큼 빠름 (로컬에선 ms 단위, 체감 차이 없음).
- 실질 반영 이점: 프론트가 가장 얇다. 백엔드 Swagger와 같은 주소를 쓰므로 디버깅이 쉽다.
- 비용·리스크: 반나절. `NEXT_PUBLIC_` 값은 빌드 때 고정돼 compose(브라우저는 `localhost:8000`, 컨테이너는 `backend:8000`)와 배포마다 이미지를 다시 빌드해야 한다.
  백엔드 주소·포트가 브라우저에 노출되고, 이후 인증을 붙일 때 키를 브라우저에 둘 수 없어 결국 프록시가 필요하다.

## Recommendation
**Option A.** 지금 백엔드는 노드 이벤트 몇 개 + 결과 한 번이라 SDK 없이 20줄 파서로 충분하고, 프록시 구조라 compose·로컬 dev·이후 배포에서
같은 이미지가 런타임 env만으로 동작한다. B는 토큰 스트리밍이 생길 때(종합 단계) 얹으면 되고, C는 빌드 고정 env와 주소 노출 때문에 배포에서 되돌려야 한다.
