# T2-18 LangChain RAG 기본 틀

## Goal
- 완료 기준 (TASK.md 그대로): `src/kosis_rag/` 모듈(로더·문서화·검색기·체인·LangChain tool) + `notebooks/rag_skeleton.ipynb` 하나에서 import해 질의→후보 표→출처 포함 답까지 실행, 표 ID 보존, 답 없음 경로, 오프라인 pytest 1개+
- Baseline: baseline 없음 (골든셋 T2-02, 하네스 T2-03 미완). 이 태스크는 T2-04~T2-10이 끼워 넣을 골격이다.

## Idea
실습 자료(ch2)의 흐름 = 로드 → 전처리 → 청킹 → 임베딩/색인 → 검색기 → 프롬프트 → LLM → 답. Gradio(2.7.7)는 제외하고
프론트(Next.js)는 T2-11에서 붙인다. KOSIS에 맞게 바꾸는 점:

1. **로더/파서 선정 — 실전 1 출력 형식 기준.** 실전 1이 만든 `data/tables.csv`(2,364행)가 이미
   `kosis_ai.schemas.TableInfo` Pydantic 스키마와 1:1이다. PDF/TextLoader 대신 csv → `TableInfo.model_validate(row)`로
   읽는다 (검증 재사용). `TableInfo.to_source().citation()`이 출처 문자열을 코드로 만든다 (LLM이 출처를 쓰지 않음).
2. **청킹 없음: 표 1건 = Document 1건.** 표 메타는 짧다(표명·조사명·기관·수록기간·메뉴경로). 텍스트 분할기를 쓰면
   표 ID가 여러 청크로 흩어져 Hit@k 계산이 꼬인다. `metadata`에 `key, org_id, tbl_id, url, period`를 넣어 보존.
3. **스키마:** `TableCandidate`(tbl_id, org_id, table_name, survey_name, organization, period, url, score, citation)와
   `SearchResult`(question, candidates, no_answer, answer)를 `src/kosis_rag/schemas.py`에 Pydantic으로 추가.
   공용 `kosis_ai.schemas`는 수정하지 않는다 (깨는 변경 없음).
4. **LLM:** 새 SDK를 들이지 않고 실전 1의 `LLMClient`(`build_client`: HCX / mock)를 `RunnableLambda`로 감싼다.
   mock 백엔드로 오프라인 실행·테스트가 된다.
5. **tool 형식 (observability·evaluation):** 공개 API를 LangChain `@tool`(`args_schema`=Pydantic, 반환=Pydantic dict)로
   정의한다. LangChain 콜백/LangSmith·OpenTelemetry가 tool 이름·입력·출력을 run 단위로 남기고, T2-03 하네스는
   같은 tool을 `tool.invoke({...})`로 호출해 후보 tbl_id 리스트로 Hit@k를 계산한다. 실전 1 `_Calls.span`과 같은
   span 모양(name, duration_ms, attributes)을 콜백 핸들러 하나로 기록한다.
6. **노트북:** `notebooks/rag_skeleton.ipynb` — 셀 순서는 실습 자료와 같다 (로드 → 점검 → 문서화 → 색인 → 검색 → 체인 → tool 호출 → 답 없음 테스트).

## Option A — 최소안: BM25 검색 tool만 (LLM 없음)
- 접근: tables.csv → TableInfo → Document → `BM25Retriever`(langchain_community + rank_bm25, 한국어는 문자 bi-gram 토크나이저) →
  `search_tables` `@tool`. 답 문장은 코드 템플릿("추천 표: … 출처: …"). 답 없음은 점수 0이면 no_answer.
- 예상 성능 향상: 지표 없음 (골든셋·하네스 전) → BM25 기준 수치는 T2-04에서 측정. 가설: 표명 직접 질의에 강하고 개념어에 약함 (미측정).
- 실질 반영 이점: 오프라인·무비용, 하네스(T2-03) 연결이 가장 빠름. 기술 설계 점수(tool 계약) 확보.
- 비용·리스크: 0.5일. 실습 자료의 임베딩·프롬프트·LLM 부분이 빠져 "RAG 챗봇 틀"로는 미완. T2-05/T2-11에서 다시 붙여야 함.

## Option B — 균형안: 검색기 교체 가능한 RAG 체인 + tool 2개
- 접근: A의 로더·문서화 + BM25 검색기. 체인·tool은 LangChain `BaseRetriever`를 인자로 받으므로 T2-05에서 Chroma를
  팩토리 없이 그대로 꽂는다 (지금 chromadb 의존성 추가 안 함). LCEL 체인 `retriever → format_context → ChatPromptTemplate("검색 결과에 없으면 없다고") → 실전1 LLMClient`.
  tool 2개: `search_tables(question, k) -> list[TableCandidate]`, `answer_table_question(question, k) -> SearchResult`.
  출처는 코드가 후보에서 붙인다. 답 없음: 질문 토큰 중 표 문서에 하나도 안 걸리면(BM25 점수 0, 쿼리 간 비교가 필요 없는 정의) → LLM 호출 없이 거절.
  점수 임계값 보정은 T2-09, 기간·주기 불일치 거절은 T2-14/T2-09로 미룸 (문서에 TODO 명시).
  LLM 답 검증: 답 문장의 표 ID·연도가 후보에 없거나 `LLMClient` status≠ok면 코드 템플릿 답으로 대체.
  관측: 새 콜백 핸들러 없이 LangChain 기본 run 트리(tool·retriever·runnable 이름)와 실전 1 `LLMClient` 기록을 그대로 쓴다.
- 예상 성능 향상: 지표 없음 → T2-04(BM25)·T2-05(임베딩)·T2-06(하이브리드)가 `kind`만 바꿔 같은 골든셋으로 측정. 답 없음 F1 측정 경로가 생김 (T2-09).
- 실질 반영 이점: 실습 자료 전 과정(Gradio 제외) 재현, 데이터 정확성(표 ID·출처 코드 생성)·예외 처리(답 없음 경로)·기술 설계(tool 계약) 동시 충족. tool이 종합 단계 에이전트에 그대로 들어감.
- 비용·리스크: 1일. 의존성 추가(langchain-core, langchain-community, rank-bm25, ipykernel). 임베딩·Chroma는 T2-05. 오프라인 pytest는 TableInfo로 검증되는 소형 fixture CSV 사용 (data/ 없는 checkout 대비).

## Option C — 고성능안: B + 실전 1 계산 tool + 에이전트형 라우팅
- 접근: B + `summarize_stat(question, table_id)` tool (실전 1 `StatPipeline`로 parquet 로드·전처리·계산·검증 재사용) +
  LLM tool-calling으로 "표 찾기 → 수치 요약" 2단 호출. 표 문서 텍스트에 `table_metadata/*.json`의 분류명·항목명을 추가(파서 확장).
- 예상 성능 향상: 미측정 가설 — 분류·항목명을 문서 텍스트에 넣으면 개념어 질의 Hit@k가 오를 것 ('성별·연령별' 등이 분류에만 있음). T2-04 이후 측정.
- 실질 반영 이점: 종합 단계 데모를 앞당김.
- 비용·리스크: 2일+. HCX tool-calling 지원·LangChain 연동 검증 필요, LangGraph는 종합 단계 범위(CLAUDE.md)라 범위 침범. 메타 JSON 파서는 T2-01(데이터 엔지니어링)과 겹침. 마감 위험.
