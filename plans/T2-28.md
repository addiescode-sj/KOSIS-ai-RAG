# T2-28 ⭐ 계층별 평가 기준 합의 (AI 평가 × 데이터) — L0 메타데이터 품질 추가

## Goal
- 완료 기준 (TASK.md 그대로): 합의 문서, evaluator pytest(oracle 1.000), "무엇을 바꿔서 몇 → 몇" 표
- 하위 이슈 순서: KOS-98 L0~L4 지표 문서 → KOS-100 임도유 리뷰·승인 → KOS-99 골든셋 슬롯 정답 라벨 117문항 + 사람 검수 20문항
  → KOS-104 필터 recall·슬롯 정확도·L0 evaluator → KOS-105 필터 전→후 평가 리포트
- 이번 세션 범위: **KOS-98** (마감 11/02, 완료 조건 "문서 1건(docs/)과 B2 리뷰 요청"). 대상 문서 `docs/research/langchain_eval_design_kosis.md`.
- 배경: 멘토링 Q1 "계층별 평가 유지". 데이터 엔지니어(임도유)가 T2-30에서 표별 메타데이터 필드

  T2-29가 질문 슬롯으로 where 필터를 건다. 필터가 정답 표를 떨어뜨리면 검색 지표가 내려가도 원인이
  메타데이터(L0)인지 슬롯 추출(L2)인지 검색(L1)인지 구분이 안 된다 → L0 계층을 추가하고 필터 recall을 L1에 넣는다.
- Baseline (고정, `plans/T2-05.md`): dev 답 있음 29문항, 컬렉션 `kosis_a_kure_202610291341`
  - BM25 Hit@1/5/10 8/13/13, MRR 0.316
  - 벡터 KURE-v1 Hit@1/5/10 10/13/15, **MRR 0.401** ← 필터 전→후 비교 기준선
  - L0·필터 recall·L2 슬롯 정확도: baseline 없음 (필드가 아직 없음)

## Idea
문서는 "LangChain 환경 Eval 설계 가이드"(일반론)인데, 실제 운영 기준은 `evals/`(T2-03)와 plan들에 흩어져 있다.
데이터 엔지니어와 합의하려면 계층마다 **무엇을 · 어떤 정답으로 · 어떤 식으로 · 누가 만든 파일로** 재는지가 한 문서에 있어야 한다.

계층 정의 (문서에 넣을 내용):

| 계층 | 대상 | 지표 | 정답 | 산출 담당 |
| --- | --- | --- | --- | --- |
| **L0 메타데이터 품질 (신규)** | T2-30 표별 메타데이터 2,364건 | 필드별 채움률, 정규화 정확도(표본), 미매핑 비율, 골든 정답 표 필드 채움률, 적재 건수 일치 | 필드 스키마(KOS-96) + 사람 검수 표본 | 데이터(필드·사전) / 평가(채점) |
| L1 검색 | `search_tables` | Hit@1/5/10, MRR, 답 없음 P/R/F1 (유형별) + **필터 recall**(정답 표가 where 필터를 통과한 비율), 필터 후 후보 수 | `required` 슬롯 | 평가 |
| L2 질의 이해 | 조건 파서 `parse_query` (T2-14, PR #17) | year·cycle·region·dimension·measure 필드별 정확도, 전 필드 일치율 | 슬롯 라벨 117문항(KOS-99) | 평가 |
| L3 계산 | `summarize_stat` (표 oracle) | 기존 유지 (사실 일치·수치 근거·거절) | `calculation_golden.jsonl` | 평가 |
| L4 종단 간 | 검색 1위 표 → `summarize_stat` | 기존 유지 + 템플릿 답변 슬롯 일치 | L3 정답 + L1 슬롯 | 평가 |

핵심 정의:
- **필터 recall** = **답 있음 전 문항**(dev 29) 중 *모든* 정답 슬롯이 필터 결과에 하나 이상의 키로 남은 문항 비율
  (multi_table은 Complete처럼 슬롯별). 필터가 안 걸린 문항은 분모에서 빼지 않고 통과·후보 2,364로 센다.
  필터는 두 갈래 — *정답 슬롯 필터*(KOS-99 라벨 → L0 오류만)와 *예측 슬롯 필터*(추출기 출력 → L0+L2 오류), 차이가 슬롯 추출 비용.
  필터를 끄면 recall 1.0이므로 **필터 후 후보 수 중앙값**을 함께 두고, 비교는 "recall과 후보 수 중앙값" 한 쌍으로만 한다.
- **기간 불일치 거절**: 완화가 거절을 덮지 않는지 — `no_period` 문항의 최종 거절률을 L1(답 없음 판정)과 L4(outcome)에 넣는다.
- **미매핑 비율** = (사전에 없는 원본 라벨 + "기타"류 포괄 값으로 보낸 라벨) / 원본 라벨. 주 지표는 **골든 정답 표 기준**, 전체 고유 라벨 기준은 병기.
- **정규화 정확도** = 표본 **n=50표**(기관별 층화, 골든 정답 표 전부 포함)를 **평가 담당이 독립 라벨링**해 데이터 산출물과 대조한 필드별 일치율.
  만든 사람이 정답을 달지 않는다.
- **템플릿 답변** = "{연도}년 {지역}의 {지표명}은 {값}{단위}입니다." / 값이 없으면 거절 템플릿("{연도}년 {지역} {지표명} 자료가 없습니다 — 사유").
  값·단위 채점은 문장이 아니라 `StatAnswer.facts`를 L3 채점기로(순환 채점 방지). 연도·지역은 L2 슬롯 라벨과 정규화 후 정확 일치,
  지표명은 표 키 단위로만 본다(표 키가 정답 슬롯에 있으면 일치) — 문자열 지표명 비교는 하지 않는다. LLM 문장은 채점하지 않는다.

순서: 문서(KOS-98) → 리뷰(KOS-100) → 슬롯 라벨(KOS-99) → evaluator(KOS-104) → 리포트(KOS-105).
L0 evaluator는 T2-30 필드 스키마가 확정돼야 짤 수 있어 KOS-104에서 한다. 문서는 필드명만 KOS-96을 따른다.

## Option A — 기존 가이드에 L0·필터 recall 절만 추가
- 접근: 문서 구조(일반 가이드)는 그대로 두고, §2 계층 표에 L0 행 추가, L1에 필터 recall 한 줄, L3/L4에 템플릿 한 줄, 기준선 한 줄.
- 예상 성능 향상: 지표 직접 변화 없음. KOS-105에서 필터 전→후 MRR 0.401 → ?을 잴 수는 있으나, 하락 시 L0/L2 원인 분리는
  정의가 없어 리포트마다 즉석으로 정하게 된다.
- 실질 반영 이점: 30분. 리뷰어가 볼 분량이 적다.
- 비용·리스크: 산출 담당·파일 계약·표본 크기·필터 recall 두 갈래가 빠져 KOS-100 리뷰에서 다시 질문이 나온다. 가이드의
  예시 코드(가상 디렉터리 `backend/evals`)가 실제 `evals/`와 달라 혼동이 남는다.

## Option B — 문서를 "KOSIS 계층별 평가 기준(L0~L4)"으로 재구성 (추천)
- 접근: 같은 파일을 프로젝트 기준 문서로 고친다. 일반론(LangChain 전후 비교·도구 책임·CI)은 1~2절로 압축하고, 계층마다
  대상 / 골든셋 파일·문항 수 / 지표 정의(식) / 채점 위치(`evals/evaluators/*.py`) / 산출 담당 / 현재 수치를 표로 둔다.
  추가 절: L0 메타데이터 품질, 필터 recall(정답 슬롯·예측 슬롯 두 갈래 + 후보 수), 데이터 × 평가 파일 계약표
  (데이터 엔지니어가 넘길 필드·사전·표본 파일), 고정 기준선, "무엇을 바꿔서 몇 → 몇" 리포트 양식, 리뷰 요청 항목(KOS-100용 체크리스트).
  가이드의 가상 디렉터리·예시 코드는 실제 `evals/` 구조와 실제 함수 이름으로 바꾼다.
- 예상 성능 향상: 문서 자체 지표 없음. 다음 단계 영향 — KOS-105에서 필터 전→후 MRR 0.401 → ?의 변화가 생기면
  필터 recall(정답 슬롯 vs 예측 슬롯)로 L0·L2 원인을 바로 나눌 수 있다(근거: T2-05에서 연도 strict 필터가 정답 2문항을
  지운 사례 — 이런 손실을 지금은 수작업으로 찾았다). KOS-104 evaluator가 문서 정의를 그대로 코드로 옮기면 된다.
- 실질 반영 이점: 결과 검증·기술 설계 항목 + 협업(20점) 근거(데이터 엔지니어와 합의한 계약표). 종합 단계에서 툴 호출 에이전트가
  필터를 쓸 때도 같은 L0/L1 지표를 재사용. 발표 자료의 평가 체계 슬라이드 원본.
- 비용·리스크: 1.5~2시간. T2-30 필드 스키마(KOS-96)가 바뀌면 L0 표 필드명만 고치면 됨(정의는 필드 중립). 11/02 마감 안.

## Option C — 문서 + 스키마·evaluator 골격까지 (계약을 코드로 먼저)
- 접근: B의 문서에 더해 `evals/schemas.py`에 `MetadataQualityItem`(L0), `QueryItem`에 `dimension` 필드 추가,
  `evals/evaluators/metadata.py`·필터 recall 함수와 pytest를 이번에 같이 만든다(KOS-104 일부 선행).
- 예상 성능 향상: B와 동일 + KOS-104 착수 시간 절약. oracle 1.000 테스트를 오늘 확보.
- 실질 반영 이점: 문서와 코드가 동시에 리뷰돼 정의 불일치가 없다.
- 비용·리스크: 4~5시간. `QueryItem` 변경은 L2 계약 변경(사용처는 아직 없음 — T2-14 미착수)이라 승인 필요.
  T2-30 필드 스키마가 아직 확정 전이라 L0 스키마를 두 번 고칠 위험이 크다. 리뷰(KOS-100) 전에 코드를 쓰는 셈이라 순서가 뒤집힌다.

## Recommendation

## 핵심 설계 (모든 옵션 공통)
- **src를 고치지 않는다.** 평가 러너는 슬롯 출처(정답 라벨 또는 `parse_query` 출력)로 `ParsedQuery`를 만들고, 끈 필드는 비운 뒤
  `.to_filter("hard")`를 부른다. `TableFilter`를 직접 만들지 않는 이유는 연도 strict/partial 규칙을 `to_filter`와 똑같이 따르기 위해서다.
  만든 필터는 `with_filter(f, records_dict)`에 넘긴다.
  - 결과는 `MAX_RESULTS`=10으로 자르고 `--k`는 10으로 고정한다. 그래야 `none`도 같은 길이로 잘린다.
  - 슬롯별 기여도는 **Chroma 경로만** 쓴다. BM25는 `ConditionRetriever`가 상위 20개를 받은 뒤 거르는 구조라 "필터 먼저"와 같지 않다.
  - 동치 확인: "예측 + 전부" 조합이 `ConditionRetriever`와 같은지 본다. 오프라인 pytest에서는 `with_filter`를 가진 가짜 base로 확인한다.
- **실행 전 확인:** 컬렉션 문서 수가 2,364이고 키 집합이 `tables.jsonl`과 같아야 한다(L0 적재 일치). 다르면 `$in` 결과와 필터 recall이 어긋난다.
- **필터 recall은 검색 없이 잰다.** `filter_tables(records, f)`를 2,364표 전체에 적용하고, 남은 표에 각 표 슬롯의 키가 있는지 본다. `MAX_RESULTS` 10개로 잘린 결과에서 재지 않는다.
  후보 수는 통과한 표 수다.
- 채점은 결정적 코드로 하고 LLM 호출은 0이다. 같은 dev 29문항에서 짝지어 비교한다. test는 채택 조합을 정한 뒤 한 번만 돌린다.

## Option A (구현) — 필터 recall + 슬롯별 기여도만
- 접근: `evals/evaluators/retrieval.py`에 `filter_recall()`, `evals/runners/ablation.py`(조합 실행·뒤집힘·판정), `run_eval --layer l1 --slots <조합> --slot-source gold|pred`.
  정답 슬롯은 받은 `query_golden.jsonl`의 기간·주기·시도 3개만 쓰고, dimension·measure는 예측 슬롯 갈래로만 돈다. L0·L2 evaluator는 미룬다.
- 예상 성능 향상: 지표를 올리는 작업이 아니라 처음 재는 작업이다. 예상치는 다음과 같다.
  - 슬롯별 판정: year·cycle은 "도움"(PR #17: 주기 조건 3문항 순위 밖 → 1위, Hit@1 +4), region은 "불분명"(dev 5문항, 순위 변화 0)
  - measure는 concept 유형(Hit@5 4/9)에서 효과가 있을 수 있다. 근거는 세는 대상이 2,071표에 채워져 있다는 것뿐이고, 측정한 적은 없다.
- 실질 반영 이점: 사용자가 요청한 "어느 슬롯이 검색을 올렸나"를 오늘 바로 답할 수 있다. 비용이 가장 작다(검색만, LLM 0).
- 비용·리스크:
  - 반나절.
  - dimension·measure는 정답 갈래가 없어서, 효과가 없을 때 메타데이터(L0) 탓인지 파서(L2) 탓인지 가를 수 없다. 문서 §4.4의 두 갈래 비교 중 절반만 남는다.
  - 문서가 약속한 L0·L2 evaluator와 oracle 1.000 pytest가 빠져 T2-28 완료 기준을 못 채운다.

## Option B (구현) — 평가 쪽 L0~L2 전부 + 슬롯별 기여도 (추천)
- 접근 (순서대로):
  1. **스키마**: `QueryItem`에 `years`·`dimensions`·`measures`를 추가한다. 기본값을 빈 목록으로 두어 기존 파일과 호환되고, 이름은 `ParsedQuery`와 같다.
     계약 변경이지만 지금 `QueryItem`을 읽는 코드가 없어 영향 범위는 `evals/schemas.py`와 테스트뿐이다.
  2. **L2 라벨 (KOS-99)**:
     - 받은 초안 117문항에 dimension·measure 라벨을 평가 쪽이 독립적으로 단다.
     - **라벨은 파서 어휘가 아니라 질문의 뜻으로 단다.** `DIMENSION_WORDS`(16개)·`MEASURES`(4개)를 기준으로 삼으면 정답이 파서를 따라가서
       L2 정확도가 부풀고 L2 몫이 작게 나온다. 파서가 모르는 표현(가구주 연령, 소득분위, 고용률 등)도 라벨에 넣고, 이것을 파서 어휘 밖 문항으로 따로 센다.
     - 형식:
       - dimension: 정규화한 분류 이름 목록(성·연령·시도 …)
       - measure: 개념 1개(출생·혼인 …). 예측 확장어 `["출생","출산","생아"]`는 개념이 목록에 있으면 정답으로 친다.
       - years: 질문에 적힌 연도(범위는 양 끝, `parse_query`와 같다). 범위는 `period_start`·`period_end`로 따로 채점한다.
     - 질문에 없으면 빈 목록이다.
     - 사람 검수 20문항(test)은 평가 10, 데이터 10으로 나누되 본인이 만든 라벨은 본인이 검수하지 않는다. 일치율을 기록한다.
  3. **L2 evaluator** `evals/evaluators/query.py` + `--layer l2`:
     - 필드별 정확도: 목록은 집합 일치 + P/R
     - 빈 슬롯도 채점한다. 정답이 빈 필드에 값을 내면 오답이다.
     - 전 필드 일치율을 낸다.
  4. **L1 필터 recall**:
     - `filter_recall()`: 표 슬롯이 전부 통과해야 성공, 필터가 없으면 통과에 후보 2,364
     - 후보 수 중앙값과 문항별 제외 사유(`why_excluded`)를 결과에 남긴다.
     - `no_period` 8문항의 거절률은 필터 0건이거나 1위 점수가 τ 미만이면 거절로 센다.
     - **τ는 `none` 조합에서 dev로 한 번 고르고, 모든 조합에 `--tau`로 고정한다.** 조합마다 τ를 다시 고르면 거절률 차이에 τ 변화가 섞인다.
       "필터 0건" 거절은 연도 슬롯이 켜진 조합에서만 생긴다고 리포트에 적는다.
     - 단계적 완화(T2-29)는 아직 코드가 없다. 지금은 "완화 없음"으로 기록하고, T2-29가 들어오면 완화 단계 필드를 추가한다.
  5. **슬롯별 기여도** `evals/runners/ablation.py`:
     - none / only:s ×5 / all / all-s ×5 = 12조합, 정답·예측 두 갈래
     - ΔMRR·ΔHit, 뒤집힌 문항 ID, 슬롯이 있는 문항만 본 조건부 효과
     - 판정 규칙(도움/불분명/해로움)은 문서 §4.4를 그대로 쓴다.
  6. **L0 evaluator** `evals/evaluators/metadata.py` + `--layer l0`:
     - 지금 필터가 쓰는 판단 함수(`table_roles`·`table_regions`·`periods`·`cycle`)로 2,364표와 골든 정답 표 240표의 필드별 채움률을 잰다.
     - measure와 dimension의 미매핑 비율을 잰다.
     - 정규화 정확도는 표본 50표 라벨 파일이 있으면 계산하고, 없으면 "표본 대기"로 둔다.
     - T2-30이 새 컬렉션을 적재하면 같은 함수를 Chroma 메타데이터에도 돌려 적재 일치를 본다.
  7. **pytest**:
     - oracle 1.000: L2는 정답을 그대로 넣으면 1.000, 필터 recall은 빈 필터면 1.000
     - 슬롯이 없는 문항에서 `only:s` = none
     - 평가 러너의 "예측 + 전부"와 `ConditionRetriever`의 결과가 같다.
     - 판정 규칙의 경계(순증 2/1/−1)
  8. **리포트 (KOS-105)**: dimension·measure 정답 라벨이 나오기 전후로 3슬롯 8조합 → 5슬롯 12조합을 돌리고, 문서 §9 표를 채운다. 채택 조합은 test로 한 번 확인한다.
- 예상 성능 향상: A와 같은 슬롯별 판정에 더해 다음을 처음 측정한다.
  - L2 dimension·measure 필드 정확도
  - L0 채움률. measure는 2,071/2,364 = 87.6%이고, 골든 정답 표 기준은 처음 잰다.
  - 필터 recall 두 갈래의 차이(L2 몫)
  - 채택 조합의 MRR 0.401 → ?. PR #17 로컬 0.534는 공식 값이 아니다. 지금의 `ConditionRetriever`는 dimension·measure도 hard로 걸기 때문에, 정답 표를 지우면 0.534보다 내려갈 수 있다. 이것을 찾는 것이 슬롯별 기여도의 목적이다.
- 실질 반영 이점:
  - T2-28 완료 기준(oracle 1.000 pytest, 몇 → 몇 표)을 채운다.
  - 데이터 정확성·결과 검증 항목에 쓸 수 있다. 개인 기술 성과(평가 엔지니어링)의 핵심 수치가 된다.
  - T2-09(필터 0건 거절)·T2-10(`search_tables` 필터 연결)이 같은 러너로 회귀 검사를 한다.
  - 종합 단계 툴 평가에서 L0~L2를 그대로 재사용한다.
- 비용·리스크:
  - 1.5일(11/02 오후 ~ 11/03). 임계 경로는 `query_golden.jsonl` 수령과 dimension·measure 라벨 117문항이다.
  - 라벨이 늦으면 4~6단계를 먼저 하고, 3슬롯 결과로 리포트 1차를 낸다.
  - **실행 순서:** 필터 recall과 3슬롯 기여도(정답 갈래는 기존 라벨, 예측 갈래는 5슬롯)를 먼저 낸다. 이것은 A와 같은 범위다.
    이어서 L0, L2, dimension·measure 라벨, 5슬롯 12조합을 순서대로 붙인다.
  - 스키마 변경은 이 plan 승인으로 함께 승인받는다.
