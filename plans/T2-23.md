# T2-23 ChromaDB Docker (로컬 공용)

## Goal
- 완료 기준 (TASK.md 그대로): 팀원 각자 로컬에서 같은 ChromaDB를 Docker Compose 서비스로 띄운다(볼륨 영속화, backend 접속 설정은 `.env`). 실전 2는 ChromaDB만, 관계형 DB는 실전 3
- Linear KOS-77 (Urgent, 마감 10/29, 담당 임도유). 다음 작업 KOS-78(적재, 10/30)과 T2-05(임베딩 검색, 10/31)가 이 서비스를 쓴다.
- Baseline: 벡터 저장소 없음. `docker-compose.yml`에 backend·frontend만 있고, `chromadb` 의존성도 없다(T2-18에서 일부러 뺌). 검색은 BM25뿐.

## 정해진 것 / 확인한 것
- 서버 이미지: `chromadb/chroma:1.5.9` (2026-05-05 게시, 고정 버전). 최신 태그는 `1.5.10.devNNN` 개발판이라 쓰지 않는다.
- 클라이언트: `chromadb-client==1.5.9` (HTTP 전용 경량 패키지, 서버와 같은 버전). 전체 `chromadb`는 로컬 DB 엔진까지 들어 있어 무겁다.
- 포트: backend가 8000을 쓰므로 Chroma는 호스트 `${CHROMA_PORT:-8001}` → 컨테이너 `8000`(겹치면 `.env`로 바꿈).
- 접속 주소가 두 가지다: 호스트에서 돌리는 코드(노트북·스크립트·pytest)는 `localhost:8001`, compose 안의 backend는 `chroma:8000`. `.env`에는 호스트용을 두고, compose의 backend `environment:`로 덮어쓴다(env_file보다 우선).
- 1.x 이미지는 Rust 서버라 데이터 경로가 `/data`(0.x는 `/chroma/chroma`), heartbeat는 `/api/v2/heartbeat`(v1은 410). 옛 경로에 볼륨을 붙이면 오류 없이 영속화만 안 된다 → 스모크로 확인한다.
- 이미지 안에 curl·python이 있다고 보장되지 않는다 → healthcheck 명령은 실제로 띄워 확인한 뒤 정한다. 실패하면 `service_healthy`를 기다리는 backend가 안 뜬다.
- backend Dockerfile이 `uv sync --frozen`이라 의존성 추가 시 `uv.lock`도 갱신해 커밋해야 한다.
- 데이터: Chroma 볼륨은 임베딩·메타데이터 사본이고 원본은 `data/tables.jsonl`(레포 밖)이다. 볼륨을 지워도 KOS-78 적재로 다시 만든다. 볼륨은 git에 안 들어간다(named volume).
- 이 PC의 Docker Desktop은 설치돼 있지만 꺼져 있다 → 측정할 때 켠다.

## Idea
compose에 `chroma` 서비스를 더하고, 팀이 같은 방식으로 접속하도록 접속 정보를 `.env`(`CHROMA_HOST`, `CHROMA_PORT`)로 둔다. "띄웠다"가 아니라 **"쓰고 → 다시 띄워도 남아 있다"**를 스모크 테스트로 확인한다.

## Option A — compose 서비스만
- 접근: `docker-compose.yml`에 `chroma` 서비스(이미지 고정, named volume, 포트 8001, healthcheck), `.env.example`에 접속 변수, README에 띄우는 법. 파이썬 코드는 없음.
- 예상 성능 향상: 로컬 Chroma 0 → 1 (팀 공용 정의). 영속화는 사람이 손으로 확인.
- 실질 반영 이점: KOS-78이 바로 붙을 서버가 생긴다.
- 비용·리스크: 1시간. 접속 코드가 없어서 KOS-78·T2-05·backend가 각자 클라이언트를 만들게 된다(접속 방식이 갈라짐). 영속화를 자동으로 확인하지 않는다.

## Option B — 서비스 + 접속 함수 하나 + 영속화 스모크 (추천)
- 접근: A에 더해
  1. `src/kosis_rag/vectorstore.py`의 `chroma_client()` 하나: `.env`의 `CHROMA_HOST`/`CHROMA_PORT`로 `chromadb.HttpClient`를 만든다(`anonymized_telemetry=False` 고정). KOS-78·T2-05·backend가 모두 이것만 쓴다.
  2. backend는 compose 안에서 `CHROMA_HOST=chroma`로 접속하고, `depends_on: chroma (service_healthy)`.
  3. `scripts/chroma_smoke.py`: heartbeat → 시험 컬렉션 쓰기 → `docker compose restart chroma` 후 다시 읽기 → 시험 컬렉션 삭제.
  4. pytest(오프라인): 환경 변수 → 접속 설정(host, port)이 맞게 나오는지만 본다. `HttpClient()`는 만들 때 서버에 접속하므로 테스트에서 만들지 않는다(verify.sh는 오프라인 유지).
  5. `uv.lock` 갱신(`chromadb-client==1.5.9`), 스모크 실패 시 "Docker Desktop을 켜세요" 같은 분명한 메시지.
- 예상 성능 향상: 로컬 Chroma 0 → 1, 재시작 후 데이터 유지 확인 0 → 자동 1회(스모크), 접속 방식 1곳으로 고정.
- 실질 반영 이점: 기술 설계·재현성. KOS-78(적재)·T2-05(검색)·T2-17(배포)가 같은 함수와 같은 서비스를 쓴다. 팀원은 `docker compose up -d chroma` 한 줄 + 스모크로 확인.
- 비용·리스크: 반나절 미만. 의존성 1개 추가(`chromadb-client`, numpy·opentelemetry 등을 함께 끌고 와 backend 이미지가 커짐). Docker Desktop이 켜져 있어야 스모크가 돈다(오프라인 pytest는 영향 없음). 이 PC에 uv가 없어 venv에 uv를 설치해 lock을 만든다.

## Option C — B + Docker 없는 내장 모드
- 접근: B에 더해 `CHROMA_HOST`가 비어 있으면 `PersistentClient(path=...)`(로컬 폴더)로 바꿔 Docker 없이도 돌게 한다.
- 예상 성능 향상: Docker를 못 쓰는 팀원(Windows Python 경로 문제 등)도 동작.
- 실질 반영 이점: 진입 장벽이 낮아진다.
- 비용·리스크: 반나절+. 내장 모드는 전체 `chromadb` 패키지(무거움)가 필요하고, 두 모드의 동작이 미묘하게 달라 "로컬 공용"이라는 목표(모두 같은 서버)와 어긋난다. 필요해지면 그때 추가.

## Recommendation
**옵션 B.** 목표가 "모두 같은 Chroma"이므로 서버 정의와 접속 방식을 한 곳에 고정하는 것이 핵심이다. A는 접속 코드가 사람마다 갈라질 위험이 있고, C는 두 번째 모드가 그 목표와 반대다. B는 반나절 안에 끝나고 다음 두 태스크가 바로 쓴다.
