# T2-21 문서화·Chunk·Top-K 실험 (Linear KOS-83)

## Goal
완료 기준(Linear KOS-83 그대로): 표 문서에 넣을 필드 조합(표명·조사명·분류·항목·주석), 긴 설명의 LangChain Text Splitter
chunk size·overlap(조각은 원래 표 ID에 연결), 검색 Top-K를 같은 골든셋으로 비교해 **채택값 1세트**를 기록한다.

## Context (2026-11-02 확인)
- 골든셋: T2-02 `evals/datasets/retrieval_golden.jsonl`(gitignore) 117문항 = dev 39(답 있음 29) · test 78(답 있음 60).
  변형 비교는 **dev 답 있음 29문항**으로 하고, 채택한 1세트는 test 답 있음 60문항으로 한 번 확인한다(T2-25·T2-28과 같은 규칙).
  리포트에 질문 원문·정답 표 key는 넣지 않는다.
- 기준선(벡터만, 필터 없음, dev 29): KURE-v1 Hit@1/5/10 10/13/15, MRR 0.408. 이 값은 **옛 빌드**(`kosis_a_kure_202610301530`) 수치다.
  지금 공용 서버의 최신 빌드는 `kosis_kure__meta-region-items-head-measure3__698f2a91`(T2-30 A7)이라 이 빌드로 다시 잰다.
  참고: 전민기 님 staged 검색(T2-06, 미세조정 bge-m3 + BM25 RRF + 조건 필터)은 dev 13/20/21, MRR 0.551이지만 체크포인트가 이 컴퓨터에 없다.
- **필드 조합**: T2-25에서 문서 형식을 이미 비교했다(라벨 나열 0.406 → 1+2+3 0.405 → +시도 이름 0.423, `docs/reports/t2-25-preprocessing.md`).
  메뉴 경로 줄이기도 그때 대리 평가에서 효과가 없었다. 아직 안 잰 것은 **조사명·분류 라벨·항목·measure 줄이 각각 얼마나 기여하는지**다.
  `scripts/doc_experiment.py`는 실전 1 golden40 + proxy30만 읽으므로 그대로 못 쓴다. 임베딩·순위 함수만 가져다 쓰고 골든셋 채점을 새로 붙인다.
- **주석**: `TableRecord`(T2-01)에 표 주석 필드가 없다. 수집 단계에서 주석을 받지 않았으므로 이번 실험 대상에서 빼고 이유를 리포트에 적는다.
- **chunk**: 임베딩 문서(`index.to_document`)는 최대 1,575토큰으로 KURE-v1 한도 8,192를 넘는 표가 0개다 → 지금 문서는 자를 필요가 없다.
  "긴 설명"에 해당하는 것은 모든 라벨을 담은 `search_text`(BM25 문서)다. 중앙값 554자, p90 1,564자, 최대 22,929자, 2,000자 초과 107표(911,627자).
  이 107표의 긴 부분은 대부분 읍면동·시군구 지명 라벨이고, 임베딩 문서에서는 단위 요약·100개 상한으로 잘린다.
  **효과 상한(세어 봄)**: 정답 표가 이 107표에 드는 문항 dev 4 · test 14, 그중 질문이 잘려 나간 라벨을 실제로 쓰는 문항 **dev 1 · test 2**.
  즉 chunk로 오를 수 있는 문항은 많아야 dev 1개다.
  조각 수 추정: size 500 약 2,000개, size 1,000 약 1,000개. 임베딩 시간은 글자 수에 비례해 설정당 약 7분(2,364표 약 160만 자 12분 기준).
  `langchain-text-splitters`가 설치되어 있지 않다(`langchain-core`만 있음).
- **Top-K**: 쓰이는 k가 두 곳이다. 사용자에게 보여 주는 후보 수(`SearchArgs.k` 기본 5, 최대 20)와 다음 단계로 넘기는 후보 수
  (`pipeline.SearchSettings.pool` 50, LLM 2차 20). 둘 다 근거 수치 없이 정해져 있다.
  답 없음 판정은 1위 점수(`metadata["score"]`)와 임계값으로 하므로 k를 바꿔도 입력이 같다 — 채택 k에서 답 없음 39문항 P/R이 그대로인지 한 줄 확인한다.

## Idea
1. **Top-K 곡선**: 한 번 top-50까지 받아 k = 1, 2, 3, 5, 10, 15, 20, 30, 50에서 Hit@k(답 있음 문항 중 정답 표가 k 안에 든 수)와 MRR을 계산한다.
   검색기 3개: KURE 벡터(공용 measure3 빌드), BM25(`search_text`), 둘의 RRF.
   채택 규칙(**보여 주는 k**만 채택): 다음 칸으로 갈 때 "늘어난 문항 수 ÷ 늘어난 k"가 0.2(k 5개당 1문항) 아래로 처음 떨어지는 k.
   dev와 test 곡선을 둘 다 그리고, 보고 수치는 test 값으로 한다(dev에서 고른 k의 dev 수치는 낙관적이다).
   **넘기는 k(pool)는 채택하지 않는다.** KURE 단독 곡선이 평평해지는 지점은 RRF·리랭커 뒤 지표와 다를 수 있어, 관찰값으로만 T2-07·T2-10에 넘긴다.
2. **필드 조합 (한 필드씩 빼기)**: 지금 적재 문서(measure3, `to_document`)에서 필드 하나씩 뺀 변형 4개를 메모리에서 임베딩해 비교한다.
   변형: 조사명 줄 빼기, 분류 라벨 빼기(분류 이름만 남김), 항목 줄 빼기, 맨 앞 measure("세는 대상") 빼기. 시도 이름·메뉴 경로는 T2-25 결과를 인용한다.
   **변형끼리는 메모리 순위로만 비교한다.** 메모리 기준과 Chroma(HNSW 근사) 값은 이미 어긋나므로(T2-25 0.406 vs 0.408) 둘을 섞지 않는다.
3. **chunk**: `search_text`를 `RecursiveCharacterTextSplitter`로 자르고 조각마다 `metadata.key`에 원래 표 ID를 둔다(107표만).
   설정 2개: size 500·overlap 50, size 1,000·overlap 100. 합치는 방법 2개를 함께 잰다.
   (a) max-pool: 표 점수 = max(표 문서 점수, 조각 점수들). 107표만 후보가 여러 개라 점수가 체계적으로 오르고, 짧은 지명 조각과 긴 문서는 코사인 척도가 다르다.
   (b) RRF: 표 문서 순위 목록과 조각 순위 목록(표 ID로 합친 뒤 최고 순위)을 RRF로 합친다. 척도 차이를 피하는 대조군이다.
   어느 쪽이든 **순위가 바뀐 문항에서 107표 쪽으로 쏠렸는지**(정답이 밀려난 문항 수, 107표가 top-10에 새로 들어온 수)를 센다.
4. **채택값 1세트**: 필드 조합 1개 + chunk 설정(또는 "자르지 않음") + 보여 주는 k. 채택 규칙: dev 29문항에서 1문항 차이는 잡음으로 보고
   "같거나(±1문항) 나으면 짧은/단순한 쪽"을 고른다. 채택 1세트만 test 60문항으로 확인.
5. **산출물**: `scripts/doc_topk_experiment.py`(실행 스크립트, 결과 `data/doc_topk/`는 gitignore), `docs/reports/t2-21-doc-chunk-topk.md`(집계만).
   적재 형식(`index.DOC_FORMAT`)·검색기 기본값은 이 태스크에서 바꾸지 않는다. 채택값을 리포트로 넘기고 반영은 T2-10(전민기)·T2-12에서 정한다.
6. pytest: 조각 → 표 ID 합치기(max-pool·RRF), Hit@k 곡선 계산, k 채택 규칙.

## Option A — Top-K 곡선만 새로 재고, 필드·chunk는 기존 근거로 정리
- 접근: Idea 1 + 4(Top-K만). 필드는 T2-25 결과를, chunk는 효과 상한(dev 1 · test 2문항)과 토큰 한도 초과 0표를 근거로
  "지금 형식 유지·자르지 않음"을 기록한다. 새 의존성 없음.
- 예상 성능 향상: 검색 지표 자체는 그대로(같은 검색기). k 근거가 생긴다. 예시(옛 빌드 수치): Hit@5 13 → Hit@10 15.
- 실질 반영 이점: T2-10 `search_tables` 기본 k에 수치 근거(기술 설계·결과 검증), T2-12 Top-K 표.
- 비용·리스크: 1시간 이내. 필드·chunk는 같은 골든셋으로 새로 비교하지 않아 KOS-83 완료 기준을 절반만 채운다.

## Option B — A + 필드 한 개씩 빼기(4변형) + chunk 2설정 × 합치기 2방법 (추천)
- 접근: Idea 1~6 전부. A를 포함하는 상위 단계다(측정을 더한 것). KURE-v1 메모리 임베딩: 필드 변형 4개 × 약 12분 + chunk 2설정 × 약 7분, 백그라운드.
  `uv add langchain-text-splitters`로 의존성 하나를 추가한다(`pyproject.toml`·`uv.lock`).
- 예상 성능 향상: 필드 변형은 dev MRR 기준 ±0.02 안이 대부분일 것(T2-25 형식 변화 0.405~0.423). "빼도 같으면 문서를 줄인다"는 근거가 된다.
  chunk는 상한이 dev 1 · test 2문항이라 많아야 Hit +1~2이고, 107표 쏠림으로 오히려 내려갈 수 있다 — 그 결과로 "자르지 않음"을 수치로 정당화하는 것이 주된 기대다.
- 실질 반영 이점: KOS-83 완료 기준 세 가지를 모두 같은 골든셋 수치로 채운다. 필드별 기여가 T2-12와 발표의 "무엇을 바꿔서 몇 → 몇" 표가 된다(데이터 정확성·기술 설계).
- 비용·리스크: 3시간 안팎(대기 포함). dev 29문항이라 1~2문항 차이는 잡음 범위 — 리포트에 그대로 적는다. KURE 결과가 staged 검색(미세조정)에 그대로 맞는다는 보장은 없다고 적는다.

## Option C — B를 staged 검색(미세조정 bge-m3 + BM25 RRF + 리랭커) 위에서 재기
- 접근: 측정 대상 검색 경로 자체를 서비스 경로(T2-06·T2-07)로 바꾼다. 체크포인트(`EMBED_CKPT`, `RERANK_CKPT`)를 전민기 님께 받아야 하고,
  문서 변형은 `kosis_rag.text`(n3-L60) 쪽에 넣어야 한다. 이 경로에서는 pool(넘기는 k)도 RRF·리랭커 뒤 지표로 정할 수 있다.
- 예상 성능 향상: 서비스 경로 기준 수치(dev MRR 0.551)라 채택값이 그대로 쓰인다. 다만 미세조정 모델은 학습한 문서 형식에 맞춰져 있어
  형식을 바꾸면 재학습 없이는 불리하게 나올 가능성이 크다.
- 실질 반영 이점: 산출물① `search_tables`의 실제 k·pool과 바로 연결된다.
- 비용·리스크: 반나절 이상 + 체크포인트 전달 대기. 전민기 님 코드(`text.py`, `pipeline.py`)를 건드리게 되어 담당 경계를 넘는다. 오늘 마감 안에 어렵다.

## Recommendation
**Option B.** KOS-83 완료 기준(필드·chunk·Top-K를 같은 골든셋으로 비교)을 오늘 안에 모두 수치로 채운다. A는 필드·chunk를 새로 재지 않아 기준의 절반이고,
C는 다른 사람 코드와 체크포인트에 기대 마감을 넘긴다. B의 결론은 KURE 벡터 기준이라 staged 검색에 옮길 때는 다시 재야 한다고 리포트에 적는다.
