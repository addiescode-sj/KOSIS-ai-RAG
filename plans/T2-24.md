# T2-24 ChromaDB 적재 (표 1건 = 문서 1건)

## Goal
- 완료 기준 (TASK.md 그대로): `data/tables.jsonl`(T2-01, 2,364표)을 ChromaDB 컬렉션에 적재한다. 메타데이터에 표 ID·조사명·기관·수록기간·주기·링크 보존, 다시 적재해도 결과가 같다(멱등). T2-05 임베딩 검색이 이 컬렉션을 쓴다
- Linear KOS-78 (Urgent, 마감 10/30, 담당 임도유). 선행: T2-01 ✅, T2-23(ChromaDB 서비스, PR #5 리뷰 중 → 이 브랜치는 T2-23 브랜치 위에서 시작).
- Baseline: Chroma 컬렉션 0개, 적재 코드 없음. 검색은 BM25(T2-18)뿐.

## 리서치 결론 (10/29, 상세는 팀 공유 리서치 노트)
- **청킹 없음, 표 1개 = 문서 1개.** 답이 "어느 표"라 검색 단위가 표여야 Hit@k를 바로 매긴다.
- **문서 형식 D2**: 표명·조사명·기관·주제·**실제 수록기간(start~end, 주기)**·메뉴 경로 전부·항목·분류명 + 분류 라벨(분류당 100개 + "외 n개"). 실측: p50 610자, p99 1,822자, 최대 6,527자 → 8,192토큰 임베딩 모델 안에 모두 들어감. 라벨 전부를 넣으면 56표가 8,000자를 넘는다.
- 같은 이름 표 716개(329개 이름)는 **실제 수록기간을 넣으면 모두 구분된다**(충돌 0).
- 메타데이터는 스칼라만(Chroma 제약): `key`·`org_id`·`tbl_id`·`table_name`·`survey_name`·`organization`·`url`·`period`(목록 문자열, 기존 `TableCandidate` 호환)·`start`·`end`(정수, T2-14 필터)·`cycle`·`prd_se`(`|`로 이은 문자열)·`unit`·`topic`·`n_labels`. None은 넣지 않는다.
- Chroma 기본 임베딩은 영어 모델(all-MiniLM-L6-v2)이라 쓰지 않는다. 문서 ID = `key` → `upsert`로 멱등.

## Idea
`src/kosis_rag/index.py`(적재 파일 하나):
- `to_chroma(record) -> (id, document, metadata)`: D2 문서와 스칼라 메타데이터 (순수 함수, 오프라인 테스트)
- `load_tables(client, records, embed, collection, batch)`: 배치로 임베딩 → `upsert` → 개수 확인
- CLI `python -m kosis_rag.index --embed <모델> --collection <이름>`: `chroma_client()`(T2-23)로 접속
- 컬렉션 이름에 문서 형식·모델을 넣는다(예: `tables_d2_kure`). 형식이나 모델이 바뀌면 새 컬렉션으로 적재해 비교한다.

구현 규칙 (리뷰 반영):
- 메타데이터 키는 `loader._META_FIELDS`를 그대로 쓰고 `period = info.period`(목록 문자열) → 기존 `to_candidate`가 바뀌지 않고 동작. 추가 키는 `start`·`end`·`cycle`·`prd_se`·`topic`·`unit`·`n_labels`. `unit`이 None인 표(891개)는 키를 뺀다.
- Chroma 1.x는 컬렉션에 임베딩 함수 설정을 저장하고, 없으면 기본 영어 모델로 기록한다. `chromadb-client`에는 그 모델을 돌릴 onnxruntime이 없다 → **임베딩은 우리가 계산해 `upsert(embeddings=...)`로 넣고, 검색도 `query(query_embeddings=...)`로 한다.** 모델명·문서 형식·차원은 컬렉션 metadata에 기록하고, 거리 공간은 `cosine`으로 명시.
- 멱등: 같은 입력이면 id·문서·메타데이터가 같다(벡터는 CPU/MPS에서 미세하게 다를 수 있음). `upsert` 후 `tables.jsonl`에 없는 id는 지우고, 개수가 2,364인지 확인.
- 배치: 임베딩은 길이순으로 정렬한 작은 배치(8~16), upsert는 `client.get_max_batch_size()` 이하.
- 토큰: 문자 수가 아니라 **모델 토크나이저로 최대 문서 토큰 수를 재서** 8,192 이하인지 Result에 남긴다. sentence-transformers `max_seq_length`가 실제 값인지도 확인.
- 오프라인 검증 유지: `chromadb`·`sentence_transformers`는 함수 안에서 import, 테스트는 `to_chroma`(순수 함수)만. 모델 파일(약 2.3GB)과 HF 캐시는 레포·이미지 밖.
- `TableRecord.search_text`(라벨 전부, 최대 22,929자)는 BM25용으로 그대로 두고, 임베딩용 D2 문서는 `index.py`가 따로 만든다. 두 문서가 다르다는 점을 코드 주석과 Result에 적는다.

옵션은 **임베딩을 어디서 만드느냐**가 다르다(검색 품질 비교는 T2-05의 몫, 여기서는 적재 가능성·비용·배포 영향).

## Option A — CLOVA Studio 임베딩 v2 (API)
- 접근: `POST /v1/api-tools/embedding/v2`(입력 ~8,192토큰, 1,024차원). 실전 1의 HCX 키(`HCX_API_KEY`)와 같은 CLOVA Studio. 2,364번 호출(배치 API 없음), 호출 간격·재시도는 실전 1 HCX 클라이언트 방식.
- 예상 성능 향상: 컬렉션 0 → 2,364문서. 적재 시간은 호출 제한에 좌우(호출당 ~0.2~0.5초 가정 시 10~20분, 미측정).
- 실질 반영 이점: backend 이미지에 torch 같은 무거운 의존성이 없다 → T2-17 배포가 가볍다. 질문 임베딩도 같은 API.
- 비용·리스크: API 비용·호출 제한. 표 메타데이터(공개 KOSIS 정보)를 외부 API로 보낸다 → 팀의 데이터 반출 판단 확인 필요. 네트워크가 없으면 적재·검색 불가. 팀원마다 키 필요.

## Option B — 로컬 한국어 모델 KURE-v1 (sentence-transformers)
- 접근: `nlpai-lab/KURE-v1`(bge-m3 한국어 튜닝, 8,192토큰, 1,024차원, MIT). 로컬 CPU/MPS로 임베딩. Chroma `SentenceTransformerEmbeddingFunction`.
- 예상 성능 향상: 컬렉션 0 → 2,364문서. 모델 카드 기준 한국어 검색 벤치마크 상위(KURE-v1 NDCG 0.606 vs bge-m3 0.598). 적재 시간 M3 MacBook에서 측정(수 분 예상).
- 실질 반영 이점: API 키·비용·외부 전송 없음, 오프라인 재현 가능.
- 비용·리스크: 모델 약 2.3GB를 팀원마다 내려받는다. `sentence-transformers`+`torch`가 의존성에 들어가 backend 이미지가 커진다(T2-17 영향). 질문 임베딩도 같은 모델이 backend에서 돌아야 한다.

## Option C — 둘 다 적재 (A + B)
- 접근: 같은 적재 함수로 `tables_d2_clova`, `tables_d2_kure` 두 컬렉션을 만든다.
- 예상 성능 향상: T2-05가 적재 없이 바로 두 모델을 같은 골든셋으로 비교할 수 있다.
- 실질 반영 이점: 모델 선택(T2-05)을 측정으로 정하는 준비가 끝난다.
- 비용·리스크: A·B 비용 합. 오늘 마감(10/30) 안에는 가능하지만 두 경로를 모두 검증해야 한다.

## Recommendation
**옵션 B (KURE-v1 로컬)로 적재하고, 적재 코드는 임베딩 함수를 인자로 받게 둔다.** CLOVA 임베딩 v2와 KURE-v1은 둘 다 bge-m3 계열(1,024차원, 8k)이라 품질 차이는 작을 가능성이 크고, 어느 쪽이 나은지는 T2-05에서 골든셋으로 정해야 한다. CLOVA는 데이터 반출 판단과 키가 필요하니, T2-05 결과를 보고 필요하면 같은 명령으로 컬렉션을 하나 더 만든다(C는 A+B일 뿐이라 지금 둘 다 할 이유가 약하다).
- T2-17 영향: backend가 질문을 같은 모델로 임베딩해야 한다. `sentence-transformers`(torch)를 main 의존성에 넣으면 backend 이미지에 CUDA torch(수 GB)가 들어오므로, 별도 dependency group(`embed`)으로 분리하고 이미지 처리 방식은 T2-17에서 정한다.
