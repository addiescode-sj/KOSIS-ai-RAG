# T2-39 답변에 보여 줄 표 = LLM이 고른 표

## Goal
- 완료 기준 (TASK.md 그대로): 보여 줄 표·출처를 LLM이 실제로 고른 표로 정하고, 답변 API의 `k`는 서버 설정으로 옮긴다
  (`search_tables(question, k)`는 유지). 완료 기준: 출처 = 답변이 가리킨 표 (pytest), 출처-답변 일치율 전→후.
  리뷰 반영: "일치율"은 정의상 1이 되므로 골든 기준 지표로 바꿨다(아래 Measure 절).
- 문제 (11/03 사용자 지적):
  - 요청 파라미터 `k`(기본 5)가 "안내 LLM에 넘길 후보 수"(입력 예산)와 "답변에 보여 줄 표 수"를 겸한다.
  - 프롬프트는 LLM에게 "1~3개 골라 [번호]와 표 ID로 가리키라"고 하지만, 결과는 그 선택을 쓰지 않는다.
    - `chain.with_citations`는 항상 후보 상위 3개를 출처로 붙인다.
    - `SearchResult.candidates`와 채팅 카드는 k개 전부다.
  - → LLM이 [2]만 맞다고 해도 출처에는 [1][2][3]이 붙는다. 출처 원칙("모든 추천·답에 출처")은 지키지만, 추천하지 않은 표까지 출처로 나간다.
- Baseline: 출처 = 항상 상위 3개(LLM 선택과 무관). 출처 정밀도(출처 중 골든 정답 표 비율)·평균 출처 수는 측정한 적 없음 → 이번에 전·후를 같은 문항으로 잰다.
- 영향 범위 확인:
  - L1 평가(`evals/runners/retrieval.py`)는 `state.docs`만 써서 영향 없음.
  - `search_tables(question, k)`(CLAUDE.md 공개 API, Hit@k 채점)는 그대로 둔다.

## Idea
공통:
1. **입력 예산 `k` → 서버 설정 (깨지 않게, 리뷰 2)**
   - `SearchSettings.answer_k`(env `ANSWER_K`, 기본 5)를 새로 둔다.
   - 답변 API의 `k`는 **받되 선택 값**이다(`None` → `answer_k`). 422를 내지 않는다.
   - 그래서 프론트(`k: 5`), 툴 `SearchArgs`, `?k=` 노드 endpoint, k별 그래프 캐시가 그대로 동작한다.
   - Swagger 설명을 "안내 LLM에 넘길 후보 수(기본: 서버 설정)"로 고친다.
   - `build_graph`·`chain.answer`가 같은 기본값(5)을 써서 test_graph 동치를 유지한다(리뷰 5). `search_tables(question, k)`는 그대로 둔다.
2. **출력에 `picked` 추가**
   - `SearchResult.picked: list[TableCandidate]`(고른 표, 고른 순서)를 둔다.
   - 출처 줄과 화면의 주 카드를 `picked`로 만든다. `candidates`(넘긴 후보 k개)는 그대로 둔다(필드 추가, 비파괴).
   - 채팅은 `picked` 카드를 먼저 보여 주고 나머지는 "다른 후보 n개"로 접는다.
   - 스트리밍 중에는 카드가 없고 `result`가 와야 정해진다(리뷰 4).
3. **경로별 규칙 — 문장과 출처가 항상 같은 표를 가리키게**
   - 템플릿: `picked` = 상위 3개(템플릿 문장이 그 3개를 나열).
   - 거절(NO_MATCH, stage2 빈 선택, 후보 없음): `picked=[]`, 출처 없음, 화면은 "다른 후보 n개"만.
   - LLM 문장이 검증은 통과했는데 표를 하나도 가리키지 않으면 **템플릿으로 돌린다**(상위 3개로 대체하면 같은 불일치가 남음, 리뷰 4).
     `answer_origin="template"`이고, 이 비율을 잰다.

옵션은 **LLM의 선택을 어디서 얻느냐**가 다르다.

## Option A — 안내 문장에서 코드가 뽑기 + 프롬프트 한 줄 (최소안)
- 접근:
  - `picked_from_reply(text, candidates)`: 검증을 통과한 문장에서 후보 표를 처음 언급된 순서로 중복 없이 뽑는다.
    - ID는 기존 `_TBL_ID` 정규식을 재사용한다(한글 붙은 "표DT_X" 포함).
    - 번호는 `[n]`, `[1, 2]`, `[1]~[3]`, 전각 `［1］`을 읽는다.
    - 번호와 ID가 함께 있고 서로 어긋나면("[2] DT_A"인데 DT_A가 1번) ID를 따른다. ID가 데이터라서다.
  - **후보 수를 넘는 `[n]`**(예: 후보 5개인데 `[7]`)은 검증 실패로 친다. `unsupported_claims`에 넣으므로 스트리밍(`streamable_prefix`)에서도 화면에 안 나간다(리뷰 3).
    괄호 안 네 자리 연도(`[2023년]`)는 표 번호로 읽지 않는다.
  - **부정 언급**("[4]는 맞지 않습니다")은 정규식으로 가려내지 않는다. 대신 프롬프트에 한 줄을 더한다: "고른 표만 [번호]와 표 ID로 가리키고, 고르지 않은 표는 언급하지 마세요". 과다 선택 비율을 잰다.
  - T2-38 스트리밍 구조는 그대로다.
- 예상 성능 향상 (골든 기준, Measure 절):
  - 평균 출처 수: 3 → LLM이 고른 1~3개.
  - 출처 정밀도(출처 중 골든 정답 표): 상위 3개 기준 → picked 기준으로 오를 것으로 추정한다. 근거는 LLM이 맞다고 한 표만 남기는 것이고, 측정 전이라 수치 미정.
  - 출처에 정답 포함(recall)은 유지되거나 소폭 하락할 수 있다(LLM이 정답을 빼면).
  - 템플릿 대체율은 "가리키지 않은 답"만큼 늘 수 있다.
- 실질 반영 이점:
  - 데이터 정확성·응답 품질: 추천하지 않은 표가 출처로 나가지 않는다.
  - 표 ID는 코드가 후보와 대조해 정한다. LLM 호출 수·지연 변화 0.
- 비용·리스크:
  - 반나절~1일.
  - 프롬프트 한 줄 변경이 NO_MATCH 비율을 바꿀 수 있어 L4 재측정이 필요하다.
  - 부정 언급은 프롬프트에 기대므로 완전하지 않다(과다 선택률로 감시).

## Option B — 구조화 출력 (JSON으로 선택과 문장을 따로)
- 접근:
  - 프롬프트를 바꿔 LLM이 `{"picks": ["DT_…"], "text": "…"}`를 내게 하고, 코드가 `picks`를 후보와 대조한다(후보 밖 ID는 버림).
  - 문장과 선택이 분리돼 과다 선택이 없다. 부정 언급·번호 형식 문제가 구조적으로 없다.
- 예상 성능 향상: 과다 선택 0. 다만 JSON 파싱 실패 → 템플릿 대체율이 늘 수 있다(HCX JSON 준수율 미측정).
- 실질 반영 이점: 선택이 명시적이라 평가(정답 표를 골랐는가 = 안내 단계 Hit)를 바로 잴 수 있다. 종합 단계 툴 호출 형식과 비슷하다.
- 비용·리스크:
  - 1일.
  - **T2-38 토큰 스트리밍과 충돌**: JSON은 다 받아야 파싱되므로 `text` 필드만 골라 흘리는 스트리밍 파서가 필요하다.
  - 프롬프트 변경 → 안내 문장 품질과 NO_MATCH 비율이 바뀔 수 있어 L4 재측정이 필요하다.

## Option C — 2차 LLM 리랭커의 선택을 그대로 쓰기
- 접근:
  - `STAGE2`(HCX 리랭커, T2-07·T2-09)가 이미 표 key를 고른다(`stage2_picked_n`). 이를 기본으로 켜고, 그 선택을 `picked`로 쓴다.
  - 안내 LLM에 넘기는 docs를 고른 표로 **자른다**. `rerank_stage2`는 "고른 표 먼저, 나머지 뒤"로 돌려주므로 자르지 않으면 안내 LLM이 고르지 않은 표도 본다(리뷰 2).
- 예상 성능 향상:
  - 출처 = 리랭커 선택(구조상 일치).
  - 참고: T2-09에서 이 리랭커를 켰을 때 답 없음 F1 τ 0.474 → 0.882, Hit@1 19 → 33(test). 출처 지표와는 다른 수치라 직접 비교 불가.
- 실질 반영 이점: 선택과 답 없음 판정이 한 모델 호출에 모인다. T2-09에서 측정된 개선을 서비스 기본값으로 쓴다.
- 비용·리스크:
  - 반나절 + 설정. 기존 STAGE2를 기본으로 켜는 설정 성격이 강하다(리뷰 2).
  - **LLM 호출 1 → 2회**, 지연 p50 +1.6초(none)~+10.9초(low, T2-09).
  - 리랭커가 고르고 안내 LLM이 또 NO_MATCH를 내는 이중 거절이 생길 수 있다.
  - 리랭커가 꺼진 환경(키 없음)에선 A 같은 대체가 필요하다.

## Recommendation
**Option A.**
- 지금 프롬프트가 이미 [번호]·표 ID로 가리키게 하므로 코드 한 함수로 선택을 얻는다.
- LLM 호출·지연이 늘지 않고, T2-38 스트리밍을 건드리지 않는다.
- B의 명시적 선택과 C의 리랭커 선택은 A의 `picked` 필드 위에 나중에 얹을 수 있다(같은 출력 계약).

## Measure
1. pytest:
   - 출처 줄 = `picked` (guide·템플릿·거절 세 경로). 아무 표도 가리키지 않은 LLM 답 → 템플릿.
   - 추출 경계: `[n]`·`[1, 2]`·`[1~3]`·`[1]~[3]`·`［1］`·ID와 번호 어긋남(ID 우선)·한글 붙은 ID·중복·후보 밖 ID.
   - 후보 수를 넘는 `[n]` → 검증 실패, 스트리밍 미노출. `[2023년]`은 번호 아님.
   - `k` 생략 시 `answer_k`, 지정 시 그 값. graph == chain.answer. `search_tables(question, k)` 그대로.
2. 골든 기준 (실제 HCX, L4/e2e 골든 답 있음 문항 N개, 같은 문항으로 전·후):
   - 평균 출처 수
   - 출처 정밀도: 출처 중 골든 정답 표 비율
   - 출처 recall: 골든 정답 표가 출처에 있는 비율
   - 템플릿 대체율, NO_MATCH 비율
   - 전 = 상위 3개 출처, 후 = picked.
