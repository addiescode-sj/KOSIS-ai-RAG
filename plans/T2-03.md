# T2-03 계층별 평가 모듈 (`evals/`)

## Goal
- 완료 기준 (TASK.md 그대로): 계층별 평가 모듈 — `evals/`에 L1~L4 골든셋과 evaluator를 모듈로 분리(실전 1 하네스 미사용) — Hit@1/5/10, MRR, 답 없음 P/R/F1, 유형별 분해, 지연·호출 수
- Baseline: 실전 2 평가 모듈 없음. 측정 가능한 지표는 0개다.
  - 골든셋은 L1 검색 117문항(T2-02)만 있다.
  - 참고값: 실전 1 summarize_stat PASS 86/90(T1-27). 실전 1 하네스로 잰 값이라 새 evaluator로 다시 잰다.
- 결정 사항 (10/29, 사용자):
  - 실전 1 하네스(`vendor/phase1/eval`)를 쓰지 않는다. import도, 확장도 하지 않는다.
  - 사용자 문서 `langchain_eval_design_kosis.md`를 기준으로 계층별 골든셋을 따로 만들고, evaluator·runner·report를 모듈로 나눈다.
  - 복합 질문은 표 최대 3개.
- 이전 plan(검색 전용 `search_eval/` + 실전 1 `grade()` import, 10/29 승인)은 이 결정으로 폐기한다.

## Idea
설계 원칙(문서 "최종 의사결정"):
1. Eval 모듈은 LangChain과 독립이다. LangChain/LangGraph는 평가 대상일 뿐이다.
2. 결정적 평가를 우선한다. 표 ID·수치·스키마는 코드로 채점한다.
3. LLM judge는 문장 품질에만 쓴다(이번 범위 밖).
4. 골든셋과 데이터 버전을 고정한다.
5. Tracing(OTel, T2-15)과 채점을 분리한다.

계층과 골든셋:

| 계층 | 파일 (`evals/datasets/`, gitignore) | 한 문항 | 출처 | evaluator 지표 | runner 대상 |
|---|---|---|---|---|---|
| L1 검색 | `retrieval_golden.jsonl` | 질문 → 정답 표 슬롯(≤3), 답 없음 사유 | T2-02 117문항 이전 | Hit@1/5/10, MRR, Complete@3/10, SlotRecall@k, 답 없음 P/R/F1, unjudged@10 | `retriever.invoke(q)` (BaseRetriever 아무거나) |
| L2 질의 이해 | `query_golden.jsonl` | 질문 → 기대 필드 {기간 시작·끝, 주기, 지역, answerable} (아래 규칙) | L1 117문항에 필드 라벨 추가 | 필드별 정확도, 전 필드 일치율 | 질의 파서 함수 (T2-14 필터 규칙·T2-08 재작성이 만듦). 그 전까지는 oracle 자기검증만 |
| L3 계산 | `calculation_golden.jsonl` | 질문 + 정답 표 key → 기대 수치 fact(값·단위·시점·차원·허용오차) 또는 기대 거절 | 실전 1 골든 90문항을 **데이터로만** 변환 (Parquet 셀 값에서 생성된 정답) | 수치 정확도(허용오차 내 일치), 단위·시점 일치, 거절 정확도, 오류율 | `summarize_stat(q, 정답 key)` |
| L4 종단 간 | `e2e_golden.jsonl` | 질문 → 기대 결과(answered/refused) + 정답 표 집합 + 기대 fact | L3 90문항 + L1 답 없음 28문항 | 종단 정확도, 손실 분해(검색 miss / 계산 오류 / 거절 오류) | 검색 top-1 → `summarize_stat` |

- L4에서 검색 top-1이 정답 표가 아니면 `retrieval_miss`로 분류하고 수치는 채점하지 않는다. 다른 표의 수치를 정답 셀과 비교하면 검색 실패가 계산 오류처럼 집계되기 때문이다.
- Trajectory 평가(문서 4.4)는 LangGraph를 도입하는 실전 3에서 한다. 이번 범위가 아니다.

구조 (문서 6장을 이 레포 규칙에 맞춤):
```
evals/
  schemas.py            계층별 골든 문항 Pydantic (RetrievalItem·QueryItem·CalcItem·E2EItem) + 로더·검사
  datasets/             (gitignore) 4개 골든 + 라벨링 중간 파일(drafts, pool.csv)
  builders/pool.py      L1 풀링 라벨링 (T2-02 search_eval/pool.py 이전)
  builders/phase1.py    실전 1 골든 → L3·L4 jsonl 변환 (데이터 변환만, 실전 1 eval 코드 import 없음)
  evaluators/retrieval.py   순수 함수: 지표
  evaluators/query.py       필드 정확도
  evaluators/calculation.py fact 매칭(시점·차원) + 허용오차 비교 (문서 4.3)
  evaluators/e2e.py         결과 분류 + 손실 분해
  evaluators/stats.py       대응 bootstrap CI, McNemar (실행 간 비교)
  runners/retrieval.py      retriever.invoke 어댑터 (LangChain 접점 1곳)
  runners/stat.py           summarize_stat 호출 (L3 oracle / L4 검색 결과)
  run_eval.py           CLI: --layer l1|l2|l3|l4 --split dev|test|all --stage <이름> [--retriever ...] [--compare <이전 실행>]
  reports/              (실행 결과 폴더는 gitignore) results.jsonl · manifest.json · report.md
tests/test_evals_*.py   evaluator 순수 함수 + 스키마 오프라인 테스트 (verify.sh 포함)
```
- manifest(문서 9장): run_id, 골든 파일별 sha256(=dataset_version), `tables.jsonl` sha256(=source_snapshot), git·vendor commit, retriever 이름과 top_k, 임베딩 모델, LLM 모델, split, 문항별 latency_ms, LLM 호출 수(LangChain 콜백), 실패 사유.
- 이전 작업: `search_eval/` → `evals/`, `eval/golden/*` → `evals/datasets/`(`search_golden` → `retrieval_golden`), T2-02 리포트의 경로 갱신, `.gitignore`에 `evals/datasets/`·`evals/reports/*/` 추가.
- 실행 시점(문서 7장): 매 PR에는 오프라인 pytest(스키마·evaluator)만 돌린다. L1은 검색 로직이 바뀔 때, L3/L4는 계산 모듈·모델이 바뀔 때 수동으로 실행한다.

### 채점 규칙 (L3·L4, 결정적)
| 실전 1 kind | 문항 수 | 맞음 기준 |
|---|---|---|
| answerable | 62 | 기대 fact마다 답의 fact가 있어야 한다. 셀 fact는 `source_ref`가 같고 값이 같아야 한다. 파생 fact(계산값)는 입력 셀 집합이 같고 `round` 자릿수의 반 단위 안이어야 한다. 단위와 시점이 일치해야 한다. 답 문장 속 근거 없는 숫자는 오류로 센다 |
| not_answerable | 20 | `outcome=refused`이고 사유가 `allowed_reasons`에 있어야 한다. 거절 문구의 품질은 채점하지 않는다 |
| clarify | 3 | `outcome=clarify`이고 선택지가 2개 이상이어야 한다 |
| default_allowed | 5 | answered이면서 `default_applied`를 밝혀야 한다. fact는 answerable과 같은 규칙으로 본다 |

- 셀이 없을 때 시점만 다르면 `wrong_period`, 나머지는 `wrong_dims`로 구분한다. 이 매칭 규칙은 실전 1 `grade.py`의 규칙과 같게 **새로 구현**한다(import하지 않음, 약 150줄 중복). 이 중복은 하네스를 쓰지 않는다는 결정의 비용으로 받아들인다.
- L4 제외·판정 규칙:
  - L1의 슬롯 2~3개 문항은 L4에서 제외한다(`summarize_stat`은 표 1개만 받음).
  - L1 답 없음 문항은 어떤 사유든 거절하면 맞음으로 본다.
  - 실전 1 문항은 표를 주는 전제로 쓰였으므로 L4에서는 "정답 표가 L1 슬롯의 대체 표 중 하나여도 맞음"으로 본다. 대체 표가 정당하게 답한 경우를 `retrieval_miss`로 오인하지 않기 위해서다.
- 골든 원본 고정: 실전 1 골든은 submodule이 아니라 형제 레포(`KOSIS-ai-nlp-summary/eval/golden/*.jsonl`, gitignore)에만 있다. `builders/phase1.py`는 경로를 인자로 받고, 원본 파일 sha256을 변환된 골든의 메타 줄과 manifest에 기록한다.
- L3 교차 검증: T1-27 실행 폴더(86/90)는 이 머신에 없다. (1) 담당 팀원에게서 실행 폴더를 받아 새 evaluator로 **재채점**한다(호출 0회, 결정적 비교). 받지 못하면 (2) `scripts/stat_baseline.py`로 1회 다시 실행한다(HCX 90회). 이 경우 LLM 분산이 섞이므로 문항별 차이를 기록한다. 기대 기준은 "판정이 다른 문항마다 원인을 설명할 수 있다"이다. ±2 같은 숫자 목표는 두지 않는다.
- L2 필드는 결정적으로 비교할 수 있는 것만 둔다: 기간 시작·끝(YYYY 또는 YYYYMM), 주기 코드(Y/Q/M/F), 지역 정규화 라벨 집합, answerable. 자유 텍스트 "지표"는 뺀다. 비교 대상 출력 스키마는 T2-14 필터 규칙의 입력(질문에서 뽑은 기간·주기)으로 정한다.

## Option A — 4계층 일괄 구축
- 접근: Idea와 채점 규칙 전부를 이번에 만든다. L2 골든(117 × 필드 4개)은 Claude 초안 + 사람 표본 검수로 만든다.
- 예상 성능 향상: 측정 가능한 지표 0 → L1 8종 × 유형별, L2 필드 정확도 4종, L3 kind별 정확도, L4 종단 정확도 + 손실 분해. L4 − L3 = 검색 때문에 잃은 정확도를 처음으로 숫자로 남긴다.
- 실질 반영 이점: 문서의 계층 구조가 한 번에 완성된다. 발표에서 계층별 손실 분해를 보여 줄 수 있다.
- 비용·리스크: 작업량 추정은 L1 모듈 0.5일, L3 변환·evaluator 0.5일, L4 0.25일, L2 라벨·evaluator 0.5일로 약 1.75일이다(T2-02 실측: 117문항 작성·판정에 약 0.5일). 마감 10/30을 넘긴다. **L2는 아직 비교할 파서 출력이 없어**(T2-14 미착수), 라벨 스키마를 나중에 다시 맞춰야 할 위험이 있다.

## Option B — 단계 구축: L1·L3 먼저, L2·L4는 대상이 생길 때
- 접근: 4계층의 스키마(`evals/schemas.py`)와 디렉터리는 지금 모두 만든다. 데이터와 evaluator는 이렇게 나눈다.
  - 지금(10/30): L1(골든 이전 + evaluator + runner + report)과 L3(실전 1 변환 + evaluator + runner + 교차 검증)
  - L4: summarize_stat 연결(T2-10 검색 API 고정) 직전에 만든다. L1·L3 골든에서 자동으로 생성하므로 0.25일이면 된다.
  - L2: T2-14가 출력 형식을 정하면 그 형식으로 라벨링한다.
  - `evaluators/stats.py`(신뢰구간)는 첫 실행 간 비교(T2-04 대 T2-05) 때 넣는다.
- 예상 성능 향상: 지금 기준으로 측정 가능한 지표 0 → L1 8종 × 유형별 + L3 kind별 정확도. 나머지 지표는 A와 같고 시점만 늦다.
- 실질 반영 이점: T2-04(BM25 기준선, 10/31)가 바로 L1을 쓴다. 계층별 골든 분리라는 결정은 스키마와 파일 단위에서 지금 확정된다. 측정 대상이 없는 라벨링(L2)은 하지 않는다.
- 비용·리스크: 1일(L1 0.5 + L3 0.5)이라 10/30 마감 안이다. L2·L4가 각 선행 태스크에 붙으므로, 그 태스크들의 plan에 "L2/L4 골든 생성"을 포함해야 한다.

## Option C — pytest 기반 평가 (골든 문항 = 파라미터 테스트)
- 접근: 계층별 골든 문항을 `pytest.mark.parametrize`로 돌린다. 임계값은 assert로 걸고, 집계는 pytest json report로 한다. 별도 runner·CLI는 두지 않는다.
- 예상 성능 향상: 지표 수는 A와 같다. CI 게이트(문서 7장)를 바로 걸 수 있다.
- 실질 반영 이점: 회귀 테스트와 평가를 하나의 도구로 묶는다.
- 비용·리스크: 이 과제의 산출물은 "몇 → 몇" 비교표인데 pytest는 pass/fail 중심이다. 그래서 실행 간 비교와 유형별 리포트를 결국 따로 만들어야 한다. 합격 점수가 없는 과제라 임계값 assert의 의미가 약하다. HCX 호출이 섞인 L3/L4는 오프라인 `verify.sh`와 분리하는 마커 관리가 필요하다.

## Recommendation
**Option B.** 계층별 골든과 모듈 분리라는 결정은 지금 스키마와 디렉터리로 확정한다. 그러면서 측정 대상이 아직 없는 L2 라벨링과 L4 연결은 대상이 생기는 태스크에 붙여 마감 안에 끝낸다. A는 L2 라벨을 파서 형식이 정해지기 전에 만들어 다시 맞춰야 할 위험이 있다. C는 비교 리포트를 따로 만들어야 해서 결국 B에 테스트 실행 방식만 바꾼 형태가 된다.
